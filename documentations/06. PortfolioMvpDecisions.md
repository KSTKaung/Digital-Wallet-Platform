## 1. MVP in one paragraph
One Spring Boot 4.1.2 application (Java 21) on port 8080, organised by business domain under `com.portfolio.wallet`, backed by one PostgreSQL database with one schema per domain. Domain boundaries are enforced by ArchUnit so modules can later be extracted into the eight documented services. A React + TypeScript + Vite SPA on port 5173 is the only client. Everything runs with free, open-source tools locally (Docker Compose) and on standard GitHub-hosted runners.

## 2. Decision log

Each entry: **Original** (target doc) · **MVP decision** · **Rationale** · **Security implications** · **Limitations** · **Tests**.

### MVP-ADR-01 Single modular application — Approved
- **Original:** 8 deployable microservices; "no modular monolith" (doc 01 ADR-001, ADR-002).
- **MVP decision:** one deployable with domain modules `auth`, `user`, `wallet`, `transfer`, `ledger`, `transaction`, `notification`, `audit`, `admin`, `common`. Modules talk only through each other's application services. Mapping to target services: auth → Identity; user → Customer & KYC; wallet → Wallet; transfer → Transfer; ledger → Ledger; notification → Risk & Notification (notification part); audit, admin → Admin & Operations.
- **Rationale:** a single developer, free tooling, and correctness over operational scale; extraction path preserved.
- **Security implications:** one process and one trust boundary; internal calls are in-process, so there are no internal network APIs to protect.
- **Limitations:** no independent scaling or deployment; one failure domain.
- **Tests:** ArchUnit module-boundary and no-cycle rules; layer rules per module.

### MVP-ADR-02 One database, schema per module — Approved
- **Original:** database per service, no cross-service joins or foreign keys (ADR-004).
- **MVP decision:** one PostgreSQL database, schemas `auth`, `usr`, `wallet`, `transfer`, `ledger`, `audit`, `notification`, one Flyway stream. No foreign keys or joins across schemas; a module's repositories touch only its own schema.
- **Rationale:** atomic money transactions without distributed coordination; boundaries kept for later split.
- **Security implications:** a single application DB role. The ledger append-only rule is enforced by a trigger instead of separate role grants (see 03).
- **Limitations:** schemas share one instance and one credential.
- **Tests:** ArchUnit (repositories used only within their module); migration tests from an empty database.

### MVP-ADR-03 Atomic ledger posting — Approved
- **Original:** ledger posted asynchronously from Kafka events; `ledgerStatus` `PENDING_POST/POSTED/FAILED_POST`; reconciliation; degraded mode above 50,000 THB (ADR-010, D-01, D-06, D-13).
- **MVP decision:** wallet snapshot updates, the balanced double-entry ledger transaction, the business record and its audit row are written in **one database transaction**. `ledgerStatus` is kept in money responses for contract compatibility and is `POSTED`, returned only after a successful commit; any failure rolls everything back and returns an error. Degraded mode does not apply. A scheduled reconciliation check compares each wallet's snapshot with its ledger-derived balance and logs any mismatch at ERROR level.
- **Rationale:** strongest consistency available without a broker; removes the posting-lag window.
- **Security implications:** ledger invariants (Σ DEBIT = Σ CREDIT, amount > 0, immutable entries, unique `transaction_reference`) still hold. Immutability is enforced by a PostgreSQL trigger rejecting `UPDATE`/`DELETE` on `ledger.ledger_entries` and `ledger.financial_transactions`.
- **Limitations:** ledger posting adds latency to the money path; `PENDING_POST` and `FAILED_POST` are never emitted.
- **Tests:** rollback when ledger posting fails mid-transaction (no snapshot change, no record); balanced-entries invariant; UPDATE/DELETE on ledger rejected; reconciliation finds an injected mismatch.

### MVP-ADR-04 No internal network APIs or mTLS — Approved
- **Original:** mutual TLS and a per-caller allow-list on every service hop; `/internal/v1/**` APIs (ADR-011, D-07, D-09; doc 03 §3.6).
- **MVP decision:** internal APIs become in-process application-service calls. mTLS is **not implemented**; it is documented as a future requirement for a distributed deployment.
- **Rationale:** there is no service-to-service network traffic to authenticate.
- **Security implications:** threat T26 (rogue internal service) does not apply; T11 (internal API exposed) is replaced by "no `/internal/**` route exists".
- **Limitations:** must be revisited before any module is extracted.
- **Tests:** `/internal/**` returns 404.

### MVP-ADR-05 Gateway responsibilities inside the application — Approved
- **Original:** Spring Cloud Gateway does JWT validation, rate limiting, CORS, security headers and correlation ID (ADR-008, doc 03 §2.2).
- **MVP decision:** Spring Security (OAuth2 resource server, Nimbus JWT) plus application filters provide the same controls. The public URL contract `/api/v1/**` is unchanged.
- **Rationale:** no separate edge component is needed for one backend.
- **Security implications:** a single enforcement point remains, and `@PreAuthorize` plus ownership checks still apply.
- **Limitations:** no WAF or edge TLS locally; production needs HTTPS termination in front (see §4).
- **Tests:** 401 without/with expired/with tampered token; 403 by role; 404 for foreign resources; CORS preflight; correlation ID generated and echoed.

### MVP-ADR-06 PostgreSQL for idempotency and OTP; in-memory rate limiting — Approved
- **Original:** Redis for idempotency keys, rate-limit counters, OTP and the degraded-mode flag (doc 04 §3.4).
- **MVP decision:** `Idempotency-Key` records and hashed OTPs live in PostgreSQL. Rate limiting uses an in-memory, per-instance limiter with the documented limits (doc 02 §1.8: auth 10/min per IP, money POSTs 30/min per customer, others 300/min per user). OTP values are never logged.
- **Rationale:** no Redis; the DB unique constraint was already the final idempotency guard.
- **Security implications:** idempotency stays durable. The rate limiter is only correct for **one instance** and resets on restart.
- **Limitations:** a distributed rate limiter (Redis or edge) is required before running more than one instance.
- **Tests:** idempotent replay returns the original response; same key + different body → `409 IDEMPOTENCY_KEY_REUSED`; concurrent duplicate requests produce one transfer; rate limit returns 429 with `Retry-After`; logs contain no OTP.

### MVP-ADR-07 Domain model purity — **Proposed**
- **Original:** domain layer has no Spring/JPA/Kafka (ADR-003, doc 01 §3.4).
- **Proposed MVP decision:** the financial core (`wallet`, `transfer`, `ledger`, and `Money` in `common`) uses **pure domain models** with separate JPA entities and mappers in `persistence`. Supporting modules with little behaviour (`notification`, `audit`, user profile) use JPA entities directly; this is a documented compromise.
- **Rationale:** keeps the rules that guard money framework-free and unit-testable, without duplicating models where there is no domain logic.
- **Security implications:** none directly; it reduces the risk of persistence concerns leaking into balance rules.
- **Limitations:** mapper code in the financial modules.
- **Tests:** ArchUnit: `wallet|transfer|ledger..domain..` must not depend on `jakarta.persistence`, Spring or `..persistence..`; domain unit tests without Spring.

### MVP-ADR-08 Locking — Approved
- **Original:** optimistic locking on `wallets.version`; two-wallet movements lock in ascending wallet-id order (ADR-009, doc 01 §6.8).
- **MVP decision:** keep the `version` column (optimistic check on every snapshot update) **and** take `SELECT … FOR UPDATE` row locks on both wallets in ascending id order inside the transfer transaction.
- **Rationale:** deterministic, deadlock-free behaviour under concurrent transfers in one database.
- **Security implications:** prevents lost updates and double spend (T5, T6); `CHECK (available_balance >= 0)` stays as the last guard.
- **Limitations:** serialises transfers touching the same wallet (acceptable at MVP scale).
- **Tests (PostgreSQL via Testcontainers):** N concurrent transfers from one wallet never overdraw; opposite-direction concurrent transfers do not deadlock; total money is conserved; ledger stays balanced.

### MVP-ADR-09 Packages and module names — Approved
- **Original:** `com.platform.<service>.{domain,application,infrastructure,presentation,config,security}`.
- **MVP decision:** `com.portfolio.wallet.<module>.{web,application,domain,persistence}`, created only where needed.
- **Tests:** ArchUnit layer rules.

### MVP-ADR-10 Minimal KYC before wallet creation — Approved
- **Original:** KYC with documents, face verification and compliance approval; wallet created on `KycApproved` (D-03, ADR-013).
- **MVP decision:** the rule is kept. A customer submits a minimal KYC application (level `BASIC` or `FULL`, document type and reference); an authorised reviewer approves or rejects it with a reason; approval creates the wallet with tier limits in the same transaction. Document upload and face verification are out of scope.
- **Security implications:** money endpoints return `403 KYC_REQUIRED` and `GET /wallet` returns `404 WALLET_NOT_FOUND` before approval; decisions are audited.
- **Limitations:** no identity evidence is actually verified.
- **Tests:** no wallet before approval; one wallet per customer; rejection needs a reason; re-application after rejection; reviewer cannot approve their own application.

### MVP-ADR-11 Unified transaction history — Approved
- **Original:** per-service lists in MVP; unified `/transactions` API is Backlog (doc 02 §8).
- **MVP decision:** the read-only `transaction` module exposes `GET /api/v1/transactions` (paged, owner-only) over deposits, withdrawals and transfers.
- **Tests:** a customer sees only their own entries (404/empty for others); paging bounds 1–100.

### MVP-ADR-12 Scope reductions — **Proposed**
Out of scope for this MVP and documented as Backlog: merchant/QR payments and refunds, linked cards, bill payment and top-up, beneficiaries, MFA, devices, SMS/push, settlement.
Requirements that touch security or financial integrity are **not dropped silently**. The proposed handling, which needs approval:

| Target requirement | Proposed MVP handling |
| ------------------ | --------------------- |
| Risk evaluation before money movement; `BLOCK` changes no balance (doc 05 F-RISK) | `transfer` calls a `RiskPolicy` port with one configurable rule (amount above a configured threshold → `REVIEW` is logged and audited, never auto-blocked); `BLOCK` path implemented and tested with a test rule |
| Maker-checker for sensitive admin actions (doc 03 §3.5) | no MVP admin action needs it: no limit changes, no Premium tier, no manual adjustments. Unfreeze requires a reason and is audited |
| Step-up authentication above a threshold (BR-009) | not implemented; documented gap |
| Staff roles (doc 03 §3.2) | JWT roles `CUSTOMER`, `ADMIN`, plus `COMPLIANCE_OFFICER` for KYC decisions, so the same person isn't both operator and KYC approver |
| Field-level encryption of phone/email (doc 03 §2.2) | not implemented in the MVP; documented gap (DB at-rest encryption is a deployment concern) |
| Password reset (doc 05 F-AUTH) | included in PR 3 using the same email/OTP mechanism |

### MVP-ADR-13 Simulated deposits and withdrawals — Approved
- **Original:** deposits from bank or card through providers; withdrawals to a bank (doc 01 §4.3).
- **MVP decision:** `POST /api/v1/wallet/deposits` and `/withdrawals` move simulated funds against the `SYS-CASH-CLEARING` ledger account, with the documented rules (amount > 0, active wallet, limits, no overdraft, idempotent). **No real money is processed.**
- **Tests:** insufficient balance; daily limits; frozen wallet; idempotency; ledger entries balanced.

### MVP-ADR-14 Refresh token transport — **Proposed**
- **Original:** login/refresh return `refreshToken` in the JSON body; the SPA must not store it in `localStorage` (doc 02 §2.1, §7).
- **Proposed MVP decision:** the refresh token is set as a cookie: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`, rotated on every use and **not** returned in the body. The access token stays in the body and in SPA memory. The SPA reaches the API **same-origin** (Vite dev proxy and nginx in Compose forward `/api` to :8080), so no credentialed CORS is needed. CSRF on cookie-authenticated endpoints (`/auth/refresh`, `/auth/logout`) is mitigated by `SameSite=Strict` plus a required `X-Requested-With` header and an `Origin` allow-list check. Fallback if this proves impractical: memory-only tokens, with reload requiring login.
- **Rationale:** survives page reload without exposing the refresh token to JavaScript.
- **Security implications:** XSS can no longer read the refresh token; refresh-reuse detection revokes the token family (doc 03 §3.4).
- **Limitations:** an **API contract change** to doc 02 §2.1 (no `refreshToken` in the body). Browsers treat `http://localhost` as a secure context, so `Secure` cookies work locally.
- **Tests:** the cookie has the required attributes; refresh without the header or from a foreign Origin → 403; refresh rotation; reuse of a rotated token revokes the family; logout clears the cookie.

### MVP-ADR-15 Framework versions — Approved
- **Original:** Spring Boot 3.x (doc 01 §10).
- **MVP decision:** Spring Boot **4.1.2** (GA 2026-10-22, OSS support to 2027-07-31), Java 21, Maven Wrapper. Library versions come from the Boot BOM where managed; springdoc-openapi 3.2.0 (built against Boot 4.1.2) and ArchUnit 1.5.1 are pinned explicitly.
- **OWASP Dependency-Check is pinned to 12.2.2, not 13.0.0.** 13.0.0 sends an empty NVD API key when none is configured, NVD rejects it (`404 Invalid apiKey`), and the scan fails (upstream issue dependency-check/DependencyCheck#8715, fixed but not yet released). 12.2.2 runs without a key, as decision D7 requires, but in practice (verified 2026-10-28) the first full NVD download without a key took over 4 hours and failed at 70% with NVD rate limiting (HTTP 429). With a free NVD API key the same scan completed (3 h 38 min for the first download, 0 findings). A free key is therefore recommended locally and as the `NVD_API_KEY` repository secret in CI; the build still runs, and fails visibly, without one. The key is applied only when `NVD_API_KEY` is set (Maven profile `nvd-api-key`). Upgrade once a 13.x release is verified to run without a key.

### MVP-ADR-16 Decision register — Approved
- The decision register D-01…D-16 that used to open doc 01 (its former section 0) has been removed from that document. This document is now the single decision register for the MVP; §3 records how each original decision applies.

### MVP-ADR-17 Local infrastructure and tooling — Approved
- **Original:** Compose with Gateway, 8 services, 9 databases, Redis, Kafka, Config Server, Eureka, dev PKI, Prometheus, Grafana (doc 04 §3.1).
- **MVP decision:** Compose runs `postgres` (5432), `backend` (8080), `frontend` (5173) and optionally `mailpit` (SMTP 1025, UI 8025, profile `mail`). Configuration comes from Spring profiles and environment variables (`.env`, gitignored). No Config Server or Eureka. CI runs on GitHub-hosted runners with free tools only.

### MVP-ADR-18 Single-limit values — **Proposed / Open**
- Docs define daily limits (transfer 100,000 / 500,000 / 1,000,000 THB by tier; withdrawal 50,000; deposit 200,000) and `MAX_WITHDRAWAL_AMOUNT=50000` (doc 04 §5). They **do not define** `singleTransfer` or `singleDeposit` values ("single_* unchanged from defaults", but the defaults are not given). These values need to come from the owner before PR 4; the code will not invent them.

### MVP-ADR-19 Generic error codes and non-disclosure — Approved (owner, 2026-10-28)
- **Original:** doc 02 §1.7 maps 400/401/403/404 to meanings but names no error codes for them; foreign ids return 404 (doc 03 §3.3, T3).
- **MVP decision:** add `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404) and `METHOD_NOT_ALLOWED` (405), using the documented error body. Missing resources and other users' resources both use `ApiException.notFound()`, which returns an identical 404 body, so responses never reveal whether another user's wallet, account or transaction exists. Unauthenticated requests get the same 401 regardless of path. Validation messages name the field, never the rejected value.
- **Tests:** `GlobalExceptionHandlerTest` (400, 405, identical 404 for missing vs foreign, 500 hides internals), `JsonSecurityErrorHandlerTest` (401, 403 bodies hide exception detail), `SecurityConfigWebTest` (401 independent of path, authenticated unknown resource → generic 404).

## 4. Security controls: implemented vs future
| Control | MVP | Target / production |
| ------- | --- | ------------------- |
| Password hashing (BCrypt), lockout after 5 failures, generic login errors | Implemented | same |
| JWT access 15 min (RS256 with `kid`), refresh 7 days rotated, hash-only storage, family revocation, 30-min session inactivity | Implemented | keys in KMS, 90-day rotation |
| OTP hashed, single-use, 5 min, 5 attempts; never logged | Implemented | same |
| RBAC + ownership checks (404 for foreign ids) | Implemented | full staff role set |
| Idempotency on money POSTs | Implemented (PostgreSQL) | same |
| Ledger immutability and balance invariants | Implemented (trigger + constraints + tests) | plus DB role separation |
| Audit log for logins, password changes, KYC decisions, freeze/unfreeze, money movements, authorization failures | Implemented | 7-year retention |
| Rate limiting | In-memory, single instance | distributed (edge or Redis) |
| CORS, security headers, correlation ID, JSON logs without secrets/PII | Implemented | plus central logging |
| Secrets from environment variables; none in git (Gitleaks in CI) | Implemented | secret manager |
| HTTPS | Not locally | required for every deployed public endpoint |
| Database and actuator exposure | DB only inside the Compose network/localhost; actuator `health`/`info` only | private network, no public DB |
| mTLS, Kafka ACLs, HMAC-signed events, field-level PII encryption, KMS, WAF, step-up auth, MFA | **Not implemented** | target (docs 01, 03) |

## 5. Verification approach
Unit and integration tests (Testcontainers PostgreSQL) are the primary evidence for wallet correctness: authorization, insufficient funds, duplicate requests, rollback, concurrent transfers and balance invariants. The CI smoke test only proves the stack starts and the main flow works; it is **not** evidence of financial correctness.
