## 1. MVP in one paragraph
One Spring Boot 4.1.2 application (Java 21) on port 8080, organised by business domain under `com.portfolio.wallet`, backed by one PostgreSQL database with one schema per domain. Domain boundaries are enforced by ArchUnit so modules can later be extracted into the eight documented services. A React + TypeScript + Vite SPA on port 5173 is the only client. Everything runs with free, open-source tools locally (Docker Compose) and on standard GitHub-hosted runners.

## 2. Decision log

Each entry: **Original** (target doc) · **MVP decision** · **Rationale** · **Security implications** · **Limitations** · **Tests**.

### MVP-ADR-01 Single modular application — Approved
- **Original:** 8 deployable microservices; "no modular monolith" (doc 01 ADR-001, ADR-002).
- **MVP decision:** one deployable with domain modules `auth`, `user`, `wallet`, `transfer`, `ledger`, `transaction`, `notification`, `audit`, `admin`, `common`. Modules talk only through each other's application services. Mapping to target services: auth → Identity; user → Customer & KYC; wallet → Wallet; transfer → Transfer; ledger → Ledger; notification → Risk & Notification (notification part); audit, admin → Admin & Operations.
- **Rationale:** a single developer, free tooling, and correctness over operational scale; extraction path preserved.
- **Security implications:** one process and one trust boundary; internal calls are in-process, so there are no internal network APIs to protect.
- **Limitations:** no independent scaling or deployment; one failure domain.
- **Amendment (owner, 2026-10-30):** a `risk` module is added for risk assessment and manual review (MVP-ADR-24); it maps to the risk part of Risk & Notification.
- **Tests:** ArchUnit module-boundary and no-cycle rules; layer rules per module.

### MVP-ADR-02 One database, schema per module — Approved
- **Original:** database per service, no cross-service joins or foreign keys (ADR-004).
- **MVP decision:** one PostgreSQL database, schemas `auth`, `usr`, `wallet`, `transfer`, `ledger`, `risk` (added 2026-10-30, MVP-ADR-24), `audit`, `notification`, one Flyway stream. No foreign keys or joins across schemas; a module's repositories touch only its own schema.
- **Rationale:** atomic money transactions without distributed coordination; boundaries kept for later split.
- **Security implications:** the ledger append-only rule is enforced by a trigger instead of separate role grants (see 03).
- **Amendment (owner, 2026-10-30; doc 07 D19):**
  - **Two database roles** replace the single application role:
    - a **migration owner**, which Flyway uses and which owns the schemas;
    - a **runtime role**, which the application uses, with DML only and no ownership.
  - The runtime role therefore cannot `ALTER TABLE … DISABLE TRIGGER`. This closes the trigger-bypass risk, for example through SQL injection.
  - The append-only triggers cover the ledger tables (MVP-ADR-03), **`audit.audit_logs`** (doc 03 §7.2) and **`risk.risk_reviews`** (MVP-ADR-24), each with a `BEFORE TRUNCATE` guard.
  - Both roles are standard PostgreSQL features; no new tool is needed.
- **Role provisioning (owner, 2026-10-30):**
  - Names: `wallet_owner` (migration owner, owns every schema) and `wallet_app` (runtime).
  - `wallet_app` is **not a superuser** and has no `CREATEROLE`; a superuser could bypass triggers through `session_replication_role`.
  - Roles are cluster objects, so an init script creates them before Flyway runs: the PostgreSQL init script in Compose, and the same script in Testcontainers. Flyway cannot create the role it runs as.
  - Credentials: two pairs from environment variables, one for the Spring datasource (`wallet_app`) and one for Flyway (`wallet_owner`).
  - Grants:
    - `GRANT USAGE` on each schema to `wallet_app`;
    - `ALTER DEFAULT PRIVILEGES`, so tables created by later migrations get their grants automatically;
    - DML on ordinary tables;
    - only `SELECT, INSERT` on the append-only tables, as defence in depth on top of the triggers.
- **Limitations:** schemas share one instance; the two credentials come from environment variables.
- **Tests:** ArchUnit (repositories used only within their module); migration tests from an empty database; the runtime role cannot update or delete ledger or audit rows, or disable their triggers.

### MVP-ADR-03 Atomic ledger posting — Approved
- **Original:** ledger posted asynchronously from Kafka events; `ledgerStatus` `PENDING_POST/POSTED/FAILED_POST`; reconciliation; degraded mode above 50,000 THB (ADR-010, D-01, D-06, D-13).
- **MVP decision:** wallet snapshot updates, the balanced double-entry ledger transaction, the business record and its audit row are written in **one database transaction**. `ledgerStatus` is kept in money responses for contract compatibility and is `POSTED`, returned only after a successful commit; any failure rolls everything back and returns an error. Degraded mode does not apply. A scheduled reconciliation check logs any mismatch at ERROR level. It checks that:
  1. each wallet's `available_balance + reserved_balance` equals its ledger-derived balance (Σ CREDIT − Σ DEBIT);
  2. each `COMPLETED` deposit, withdrawal and transfer has exactly one ledger transaction;
  3. each wallet's `reserved_balance` equals the sum of its `PENDING_REVIEW` transfers;
  4. reserved daily-limit usage equals the same sum per limit date.

  (Amended 2026-10-30 for MVP-ADR-24.)
- **Rationale:** strongest consistency available without a broker; removes the posting-lag window.
- **Security implications:** ledger invariants (Σ DEBIT = Σ CREDIT, amount > 0, immutable entries, unique `transaction_reference`) still hold. Immutability is enforced by a PostgreSQL trigger rejecting `UPDATE`/`DELETE` on `ledger.ledger_entries` and `ledger.financial_transactions`.
- **Limitations:** ledger posting adds latency to the money path; `PENDING_POST` and `FAILED_POST` are never emitted.
- **Amendment (owner, 2026-10-30; doc 07 D09, revised the same day for MVP-ADR-24):**
  - The MVP transfer states are `COMPLETED`, `PENDING_REVIEW`, `REJECTED`, `CANCELLED`, `EXPIRED` and `BLOCKED` (MVP-ADR-24).
  - `PENDING` and `PROCESSING` (doc 02 §2.4) are never used.
  - Ledger entries are posted only when a transfer becomes `COMPLETED`, in the same transaction.
  - `POST /api/v1/transfers/{id}/cancel` is allowed only while the transfer is `PENDING_REVIEW`.
  - A transfer that fails validation (balance, limits, wallet status) leaves no transfer row; its audit row is written in its own transaction (doc 07 D08).
- **Tests:** rollback when ledger posting fails mid-transaction (no snapshot change, no record); balanced-entries invariant; UPDATE/DELETE on ledger rejected; reconciliation finds an injected mismatch.

### MVP-ADR-04 No internal network APIs or mTLS — Approved
- **Original:** mutual TLS and a per-caller allow-list on every service hop; `/internal/v1/**` APIs (ADR-011, D-07, D-09; doc 03 §3.6).
- **MVP decision:** internal APIs become in-process application-service calls. mTLS is **not implemented**; it is documented as a future requirement for a distributed deployment.
- **Rationale:** there is no service-to-service network traffic to authenticate.
- **Security implications:** threat T26 (rogue internal service) does not apply; T11 (internal API exposed) is replaced by "no `/internal/**` route exists".
- **Limitations:** must be revisited before any module is extracted.
- **Tests:** `/internal/**` returns 404.

### MVP-ADR-05 Gateway responsibilities inside the application — Approved
- **Original:** Spring Cloud Gateway does JWT validation, rate limiting, CORS, security headers and correlation ID (ADR-008, doc 03 §2.2).
- **MVP decision:** Spring Security (OAuth2 resource server, Nimbus JWT) plus application filters provide the same controls. The public URL contract `/api/v1/**` is unchanged.
- **Rationale:** no separate edge component is needed for one backend.
- **Security implications:** a single enforcement point remains, and `@PreAuthorize` plus ownership checks still apply.
- **Limitations:** no WAF or edge TLS locally; production needs HTTPS termination in front (see §4).
- **Tests:** 401 without/with expired/with tampered token; 403 by role; 404 for foreign resources; CORS preflight; correlation ID generated and echoed.

### MVP-ADR-06 PostgreSQL for idempotency and OTP; in-memory rate limiting — Approved
- **Original:** Redis for idempotency keys, rate-limit counters, OTP and the degraded-mode flag (doc 04 §3.4).
- **MVP decision:** `Idempotency-Key` records and hashed OTPs live in PostgreSQL. Rate limiting uses an in-memory, per-instance limiter with the documented limits (doc 02 §1.8: auth 10/min per IP, money POSTs 30/min per customer, others 300/min per user). OTP values are never logged.
- **Rationale:** no Redis; the DB unique constraint was already the final idempotency guard.
- **Security implications:** idempotency stays durable. The rate limiter is only correct for **one instance** and resets on restart.
- **Limitations:** a distributed rate limiter (Redis or edge) is required before running more than one instance.
- **Amendment (owner, 2026-10-30):** the wallet-lookup limits (MVP-ADR-20) and the OTP counters (MVP-ADR-23) are stored in **PostgreSQL**, so they hold across restarts and instances. All other limits stay in memory.
- **Tests:** idempotent replay returns the original response; same key + different body → `409 IDEMPOTENCY_KEY_REUSED`; concurrent duplicate requests produce one transfer; rate limit returns 429 with `Retry-After`; logs contain no OTP.

### MVP-ADR-07 Domain model purity — Approved (owner, 2026-10-30)
- **Original:** domain layer has no Spring/JPA/Kafka (ADR-003, doc 01 §3.4).
- **MVP decision:** the financial core (`wallet`, `transfer`, `ledger`, and `Money` in `common`) uses **pure domain models** with separate JPA entities and mappers in `persistence`. Supporting modules with little behaviour (`notification`, `audit`, user profile) use JPA entities directly; this is a documented compromise.
- **Rationale:** keeps the rules that guard money framework-free and unit-testable, without duplicating models where there is no domain logic.
- **Security implications:** none directly; it reduces the risk of persistence concerns leaking into balance rules.
- **Limitations:** mapper code in the financial modules.
- **Tests:** ArchUnit: `wallet|transfer|ledger..domain..` must not depend on `jakarta.persistence`, Spring or `..persistence..`; domain unit tests without Spring. The current domain rule does not yet forbid `jakarta.persistence` or Spring, so PR 2 extends it and adds a self-test (doc 07 D07).

### MVP-ADR-08 Locking — Approved
- **Original:** optimistic locking on `wallets.version`; two-wallet movements lock in ascending wallet-id order (ADR-009, doc 01 §6.8).
- **MVP decision:** keep the `version` column (optimistic check on every snapshot update) **and** take `SELECT … FOR UPDATE` row locks on both wallets in ascending id order inside the transfer transaction.
- **Rationale:** deterministic, deadlock-free behaviour under concurrent transfers in one database.
- **Security implications:** prevents lost updates and double spend (T5, T6); `CHECK (available_balance >= 0)` stays as the last guard.
- **Limitations:** serialises transfers touching the same wallet (acceptable at MVP scale).
- **Tests (PostgreSQL via Testcontainers):** N concurrent transfers from one wallet never overdraw; opposite-direction concurrent transfers do not deadlock; total money is conserved; ledger stays balanced.

### MVP-ADR-09 Packages and module names — Approved
- **Original:** `com.platform.<service>.{domain,application,infrastructure,presentation,config,security}`.
- **MVP decision:** `com.portfolio.wallet.<module>.{web,application,domain,persistence}`, created only where needed.
- **Tests:** ArchUnit layer rules.

### MVP-ADR-10 Minimal KYC before wallet creation — Approved
- **Original:** KYC with documents, face verification and compliance approval; wallet created on `KycApproved` (D-03, ADR-013).
- **MVP decision:** the rule is kept. A customer submits a minimal KYC application (level `BASIC` or `FULL`, document type and reference); an authorised reviewer approves or rejects it with a reason; approval creates the wallet with tier limits in the same transaction. Document upload and face verification are out of scope.
- **Security implications:** money endpoints return `403 KYC_REQUIRED` and `GET /wallet` returns `404 WALLET_NOT_FOUND` before approval; decisions are audited.
- **Limitations:** no identity evidence is actually verified.
- **Tests:** no wallet before approval; one wallet per customer; rejection needs a reason; re-application after rejection; reviewer cannot approve their own application.

### MVP-ADR-11 Unified transaction history — Approved
- **Original:** per-service lists in MVP; unified `/transactions` API is Backlog (doc 02 §8).
- **MVP decision:** the read-only `transaction` module exposes `GET /api/v1/transactions` (paged, owner-only) over deposits, withdrawals and transfers.
- **Tests:** a customer sees only their own entries (404/empty for others); paging bounds 1–100.

### MVP-ADR-13 Simulated deposits and withdrawals — Approved
- **Original:** deposits from bank or card through providers; withdrawals to a bank (doc 01 §4.3).
- **MVP decision:** `POST /api/v1/wallet/deposits` and `/withdrawals` move simulated funds against the `SYS-CASH-CLEARING` ledger account, with the documented rules (amount > 0, active wallet, limits, no overdraft, idempotent). **No real money is processed.**
- **Tests:** insufficient balance; daily limits; frozen wallet; idempotency; ledger entries balanced.

### MVP-ADR-14 Refresh token transport — **Proposed**
- **Original:** login/refresh return `refreshToken` in the JSON body; the SPA must not store it in `localStorage` (doc 02 §2.1, §7).
- **Proposed MVP decision:** the refresh token is set as a cookie: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`, rotated on every use and **not** returned in the body. The access token stays in the body and in SPA memory. The SPA reaches the API **same-origin** (Vite dev proxy and nginx in Compose forward `/api` to :8080), so no credentialed CORS is needed. CSRF on cookie-authenticated endpoints (`/auth/refresh`, `/auth/logout`) is mitigated by `SameSite=Strict` plus a required `X-Requested-With` header and an `Origin` allow-list check. Fallback if this proves impractical: memory-only tokens, with reload requiring login.
- **Rationale:** survives page reload without exposing the refresh token to JavaScript.
- **Security implications:** XSS can no longer read the refresh token; refresh-reuse detection revokes the token family (doc 03 §3.4).
- **Limitations:** an **API contract change** to doc 02 §2.1 (no `refreshToken` in the body). Browsers treat `http://localhost` as a secure context, so `Secure` cookies work locally.
- **Tests:** the cookie has the required attributes; refresh without the header or from a foreign Origin → 403; refresh rotation; reuse of a rotated token revokes the family; logout clears the cookie.

### MVP-ADR-15 Framework versions — Approved
- **Original:** Spring Boot 3.x (doc 01 §10).
- **MVP decision:** Spring Boot **4.1.2** (GA 2026-10-22, OSS support to 2027-07-31), Java 21, Maven Wrapper. Library versions come from the Boot BOM where managed; springdoc-openapi 3.2.0 (built against Boot 4.1.2) and ArchUnit 1.5.1 are pinned explicitly.
- **API docs without a bundled Swagger UI (2026-10-29).** The backend uses `springdoc-openapi-starter-webmvc-api`, not `-webmvc-ui`: the bundled `org.webjars:swagger-ui` 5.34.0 ships DOMPurify 3.4.16, which Dependency-Check flags with CVE-2026-116803 and CVE-2026-116804 (CVSS 10.0), and no fixed swagger-ui or springdoc release exists yet. The OpenAPI JSON stays available at `/v3/api-docs` in the `local` profile only; view it with any OpenAPI viewer. Bring the UI back once a release with a fixed DOMPurify passes the scan.
- **OWASP Dependency-Check is pinned to 12.2.2, not 13.0.0.** 13.0.0 sends an empty NVD API key when none is configured, NVD rejects it (`404 Invalid apiKey`), and the scan fails (upstream issue dependency-check/DependencyCheck#8715, fixed but not yet released). 12.2.2 runs without a key, as decision D7 requires, but in practice (verified 2026-10-28) the first full NVD download without a key took over 4 hours and failed at 70% with NVD rate limiting (HTTP 429). With a free NVD API key the same scan completed (3 h 38 min for the first download, 0 findings). A free key is therefore recommended locally and as the `NVD_API_KEY` repository secret in CI; the build still runs, and fails visibly, without one. The key is applied only when `NVD_API_KEY` is set (Maven profile `nvd-api-key`). Upgrade once a 13.x release is verified to run without a key.

### MVP-ADR-18 Limit values — Approved (owner, 2026-10-30)
- **Original:** docs define daily limits (transfer 100,000 / 500,000 / 1,000,000 THB by tier; withdrawal 50,000; deposit 200,000) and `MAX_WITHDRAWAL_AMOUNT=50000` (doc 04 §5), but no single-transaction or minimum values.
- **MVP decision:** all values are configuration properties, never literals.

  | Operation | Minimum | Maximum per transaction | Daily limit |
  | --------- | ------- | ----------------------- | ----------- |
  | Transfer (outgoing) | 1.00 THB | 50,000.00 THB, every tier | tiered: `BASIC` 100,000.00 THB; `FULL` (Verified) 500,000.00 THB; Premium not offered (§3, D-05) |
  | Deposit | 100.00 THB | 100,000.00 THB | 200,000.00 THB |
  | Withdrawal | 100.00 THB | 30,000.00 THB | 50,000.00 THB (= `MAX_WITHDRAWAL_AMOUNT`, doc 04 §5) |

- **Errors:**
  - below the minimum → `400 INVALID_AMOUNT`;
  - above the per-transaction maximum → `409 SINGLE_LIMIT_EXCEEDED`;
  - over the daily limit → `409 DAILY_LIMIT_EXCEEDED`.
- **Daily usage:**
  - counted per Asia/Bangkok calendar day (MVP-ADR-22);
  - includes `COMPLETED` movements, plus amounts reserved by transfers in `PENDING_REVIEW` (MVP-ADR-24);
  - rejected, cancelled, expired, blocked and failed transfers do not count (doc 01 §7.5).
- **Concurrency:** the daily usage is checked and updated under the same row locks as the wallet (MVP-ADR-08), so concurrent requests can never exceed a limit.
- **Source of values (owner, 2026-10-30):** limits are read from configuration, by the wallet tier, at check time. No per-wallet copy is stored, so a configuration change applies to every wallet at once.
- **Limit day on the record:** each transfer stores its `limit_date`, the Asia/Bangkok submission day. Capture and release always use that date, never the current day (MVP-ADR-22).
- **Tests:** boundaries at the minimum, at the maximum and at +0.01; daily limit at exactly the limit and +0.01; N concurrent transfers never exceed a limit; a held amount counts and is released on rejection, cancel or expiry.

### MVP-ADR-19 Generic error codes and non-disclosure — Approved (owner, 2026-10-28)
- **Original:** doc 02 §1.7 maps 400/401/403/404 to meanings but names no error codes for them; foreign ids return 404 (doc 03 §3.3, T3).
- **MVP decision:** add `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404) and `METHOD_NOT_ALLOWED` (405), using the documented error body. Missing resources and other users' resources both use `ApiException.notFound()`, which returns an identical 404 body, so responses never reveal whether another user's wallet, account or transaction exists. Unauthenticated requests get the same 401 regardless of path. Validation messages name the field, never the rejected value.
- **Tests:** `GlobalExceptionHandlerTest` (400, 405, identical 404 for missing vs foreign, 500 hides internals), `JsonSecurityErrorHandlerTest` (401, 403 bodies hide exception detail), `SecurityConfigWebTest` (401 independent of path, authenticated unknown resource → generic 404).
- **Deferred to PR 3 (security review of PR 1, 2026-10-29):** two error-response gaps with no impact yet, because PR 1 has no endpoints and no method security. They are fixed in PR 3, where authentication and roles make them testable:
  - *Medium:* the catch-all handler in `GlobalExceptionHandler` turns `AccessDeniedException`/`AuthorizationDeniedException` (from `@PreAuthorize`) into 500 `SYSTEM_ERROR`, and does the same for `MissingRequestHeaderException`, `MethodArgumentTypeMismatchException` and `HttpMediaTypeNotSupportedException`. **Fix:** map them to 401/403 and 400 (415 for the media type, which needs an error code entry here) with tests.
  - *Low:* errors raised before MVC (firewall rejections, exceptions thrown in filters) reach Spring Boot's default `/error` body `{timestamp,status,error,path}`, without `errorCode` or `correlationId`. **Fix:** a custom `ErrorController` that returns the documented error body, with tests.
- **Amendment (owner, 2026-10-30):** new code `INVALID_TRANSFER_STATE` (409). It is returned when a transfer is cancelled, approved or rejected while it is no longer `PENDING_REVIEW` (MVP-ADR-24).

### MVP-ADR-20 Recipient discovery by wallet number — Approved (owner, 2026-10-30)
- **Original:** `POST /api/v1/transfers` takes `receiverCustomerId` (doc 02 §2.4), and no lookup is documented. Beneficiaries are out of scope (MVP-ADR-12).
- **MVP decision:**
  - **Wallet number:** every wallet has a public wallet number, separate from its internal UUID.
    - It is unique, **immutable** (a database trigger rejects changes), random and non-sequential, with a check digit.
    - The exact format is fixed in the PR 4 plan. "Wallet ID" in the owner's decision means this number.
    - It has at least 10 random digits plus the check digit (owner, 2026-10-30).
  - **Lookup:** `GET /api/v1/wallets/lookup?walletNumber=…` does an **exact** match only.
    - It returns the recipient's **masked legal name** (first name plus the initial of the last name) and the **masked wallet number** (last 4 digits visible). The SPA shows both before the customer confirms.
    - There is **no** lookup by phone number or email.
  - **Transfer request:** `receiverWalletNumber` replaces `receiverCustomerId`.
  - **Legal name:** captured in the KYC application (MVP-ADR-10) and copied to the customer profile on approval. It is Confidential data (doc 03 §5.1).
- **Security implications:**
  - A lookup confirms that a wallet number exists. This is accepted for usability and mitigated as follows:
    - numbers are not guessable;
    - only KYC-approved callers with an `ACTIVE` wallet can look up;
    - lookups have their own rate limit;
    - every lookup is audited;
    - a missing, frozen or closed wallet, or the caller's own wallet, returns the identical `404` (MVP-ADR-19);
    - a transfer to a missing, frozen or closed wallet returns the same `404` as the lookup, never `WALLET_FROZEN`. A transfer to the sender's own wallet stays `SELF_TRANSFER` (owner, 2026-10-30).
  - The response never contains the customer id, email, phone or full name.
- **Rate limits (owner, 2026-10-30; doc 07 D26):**
  - **10 lookups per minute per authenticated user** and **30 per minute per client IP**, as sliding windows stored in PostgreSQL.
  - Successful and unsuccessful lookups both count.
  - When exceeded: `429` with `Retry-After`.
  - Enforced in the backend only.
  - The client IP comes from `X-Forwarded-For`, trusted only when set by the nginx proxy.
- **Tests:**
  - exact match only;
  - masked fields;
  - identical `404` for every non-eligible case;
  - rate limit;
  - audit row;
  - the wallet number cannot be updated;
  - a transfer to a looked-up wallet number.

### MVP-ADR-21 Money precision — Approved (owner, 2026-10-30)
- **Original:** `NUMERIC(19,4)` (doc 01 §7.4); JSON money with at most 4 decimals (doc 02 §1.6).
- **MVP decision:**
  - Every THB amount and balance is `NUMERIC(19,2)` in PostgreSQL and `BigDecimal` with scale 2 in Java.
  - A request with **more than two decimal places is rejected** with `400 INVALID_AMOUNT`, never rounded.
  - `float` and `double` are never used for money.
  - Currency is always explicit, as an ISO 4217 code (`char(3)`, `THB` only).
- **Rationale:** THB has two minor units; storing more precision invites rounding differences between snapshot and ledger.
- **Limitations:** a currency with three minor units would need a migration and a new ADR.
- **Enforcement:** PostgreSQL rounds a value to `NUMERIC(19,2)` on assignment, so the database cannot reject extra decimals. The rule is therefore enforced in the API and domain layers: `Money` uses `setScale(2, RoundingMode.UNNECESSARY)`. A test proves that a scale-3 value never reaches a repository.
- **Tests:** 2 decimals accepted; 3 rejected; amounts compared with `compareTo`, not `equals`; the database rejects nothing that the API accepts.

### MVP-ADR-22 Business time zone — Approved (owner, 2026-10-30)
- **MVP decision:**
  - Timestamps are stored in UTC (`timestamptz`).
  - Daily limits use the **Asia/Bangkok** calendar day and reset at midnight Bangkok time (17:00 UTC).
  - A transfer held for review counts against the day it was **submitted**, even if it is approved later.
  - The time zone is configuration, and the code reads time through an injectable `Clock`.
- **Tests:** a fixed clock at 16:59:59Z and at 17:00:00Z falls on different business days; a held transfer approved after midnight stays on its submission day.

### MVP-ADR-23 Authentication parameters and password hashing — Approved (owner, 2026-10-30)
- **Original:** "strong policy", lock after 5 failures, OTP 5 minutes and 5 attempts, BCrypt (doc 03 §3.4, doc 06 §4).
- **MVP decision**, all values configuration:

  | Item | Value |
  | ---- | ----- |
  | Lockout | after **5 consecutive** failed logins, for **15 minutes**; the counter resets on a successful login. It is tracked per identifier, unknown emails included. A successful **password reset clears the lock**, and the account owner is **emailed** when the lock starts. Counters for unknown emails live in their own table and are deleted after 24 hours. The limit of 10 requests per minute per IP on `/auth/**` stays (doc 02 §1.8) |
  | Password | **12–128 characters**; may not repeat any of the **last 5** passwords |
  | Password hashing | **Argon2id** (Spring Security `Argon2PasswordEncoder` with Bouncy Castle, a free dependency approved by the owner and added in PR 3). This replaces BCrypt, whose 72-byte input limit cannot hold a 128-character password. Cost parameters are configuration, defaulting to the OWASP baseline: memory 19 MiB, 2 iterations, parallelism 1. The number of hashes computed at the same time is bounded. Unknown and locked accounts still run a dummy hash, so all login failures take the same time. Length is counted in Unicode code points after NFC normalisation |
  | OTP | **6 digits**; valid **5 minutes**; at most **5 verification attempts** per challenge; resend cooldown **60 seconds**; at most **5 resends per hour**. A resend cancels the previous code. After **5 used-up challenges within 24 hours** the identifier gets no new challenge until the 24-hour window clears. `resend-otp` and `forgot-password` always return `202`, also for unknown identifiers |
  | OTP storage | keyed hash (HMAC-SHA256); the secret comes only from an environment variable. Resend and attempt counts are stored in PostgreSQL, so they survive a restart (MVP-ADR-06) |

  Passwords and OTPs are never stored, logged or returned in plain text.
- **Login response:** a wrong password, an unknown account and a locked account return the **same** `401`, so the response does not reveal whether an account exists. This changes doc 02 §2.1, which returned `403 ACCOUNT_LOCKED`. The lock is still audited.
- **Tests:**
  - lockout at the 5th consecutive failure and expiry after 15 minutes (fixed clock);
  - a success resets the counter;
  - password lengths 11, 12, 128 and 129;
  - reuse of each of the last 5 passwords rejected;
  - OTP expiry, attempt limit, cooldown and hourly cap;
  - hashes only in the database;
  - no OTP or password in the logs.

### MVP-ADR-24 Risk assessment and manual review — Approved (owner, 2026-10-30)
- **Original:** risk evaluation returns `ALLOW | REVIEW | BLOCK` (doc 02 §4.4); a block never changes balances (doc 05 §4); MVP-ADR-12 proposed a single threshold rule.
- **MVP decision:**
  - **Module:** a separate `risk` module and schema (amends MVP-ADR-01 and -02).
    - Tables: `risk_assessments` (score, band, decision, time), `risk_rule_hits` (rules triggered), `risk_reviews` (reviewer, decision, reason, time; append-only) and `investigations` (assessment, status `OPEN`/`CLOSED`, closing officer, outcome).
    - The assessment is recorded in its own transaction before any money moves.
    - **If the evaluation fails, the transfer is rejected** with `SYSTEM_ERROR`: no transfer row, no hold, no funds moved, and an audit row is written. A failed evaluation never counts as score 0.
    - Assessments of the same sender are serialised by a per-sender row lock in the `risk` schema, so concurrent requests cannot bypass the transfer-count rule.
  - **Score:** 0–100, the sum of the rule weights, capped at 100. Weights and thresholds are configuration (owner, 2026-10-30; doc 07 D27):

    | Rule | Condition | Weight |
    | ---- | --------- | ------ |
    | Transfer amount | 10,000.01–25,000.00 THB | +10 |
    | | 25,000.01–40,000.00 THB | +20 |
    | | above 40,000.00 THB | +30 |
    | Transfer frequency | 3–4 transfers within 10 minutes | +15 |
    | | 5–7 transfers within 10 minutes | +25 |
    | | 8 or more transfers within 10 minutes | +35 |
    | New recipient | first successful transfer from this sender to this recipient | +15 |
    | New wallet (sender's) | less than 24 hours old | +20 |
    | | 24 hours to less than 7 days old | +10 |

    - Only the **highest matching weight per rule** applies.
    - **Transfer frequency** counts the sender's assessed transfers in the last 10 minutes, including the current one and all outcomes (blocked and cancelled too).
    - The `transfer` module passes the facts the rules need (amount, sender wallet age, whether a completed transfer to this recipient exists). The frequency count comes from the `risk` schema's own assessments.
    - The triggered rules and each rule's score are stored in `risk_rule_hits`.
  - **Bands** (boundaries are configuration):

    | Score | Decision | Effect |
    | ----- | -------- | ------ |
    | 0–39 | `ALLOW` | normal atomic transfer (MVP-ADR-03) |
    | 40–69 | `MONITOR` | normal transfer, assessment flagged for monitoring |
    | 70–89 | `MANUAL_REVIEW` | transfer `PENDING_REVIEW`; **no money reaches the recipient** |
    | 90–100 | `BLOCK` | transfer `BLOCKED` (the row is kept), `403 RISK_BLOCKED`; no balance changes; an investigation is opened in `risk.investigations`; the wallet is not frozen automatically |

  - **Hold:** in one transaction, the amount moves from the sender's `available_balance` to `reserved_balance` (no ledger entries), and the daily limit is reserved on the submission day (MVP-ADR-22).
  - **Review:** by a `COMPLIANCE_OFFICER` (MVP-ADR-12), who may be **neither the sender nor the recipient**. Both are compared by the auth user id behind each wallet.
    - **Approve:** one transaction checks that the hold has not expired, re-checks the wallets, captures the reserved amount, credits the recipient, posts the ledger and sets `COMPLETED`.
    - If the sender or recipient wallet is frozen or closed at that moment, the transfer becomes `REJECTED` instead, and the hold is released.
    - **Reject:** `REJECTED`, and the hold and the limit are released.
  - **Cancel:** the sender may cancel while the transfer is `PENDING_REVIEW` and the hold has not expired (`CANCELLED`), even if the sender wallet is frozen. Cancelling releases the hold and the limit.
  - **Expiry (owner, 2026-10-30; doc 07 D28):**
    - A transfer may stay in `PENDING_REVIEW` for at most **24 hours**, counted from when it entered that state (UTC timestamps).
    - After **12 hours**, compliance officers are notified that it will expire.
    - No extension exists in the MVP.
    - At 24 hours it becomes `EXPIRED`: neither wallet is debited or credited, the reserved funds and the daily-limit capacity are released, and the expiry is audited.
    - Expiry is processed by a scheduled job, and is also checked during every admin action. An approve or reject that finds the deadline passed expires the transfer in the same transaction and returns `409 INVALID_TRANSFER_STATE`.
    - The job interval is configuration.
  - **Concurrency:** approve, reject, cancel and expire each run in one transaction, which also writes the `risk_reviews` row, so no review row exists for an action that lost.
    - Lock order: the transfer row `FOR UPDATE`, then the wallets in ascending id order in one SQL statement, then the limit-usage rows.
    - The first action wins; the others get `409 INVALID_TRANSFER_STATE`.
    - The expiry job handles one transfer per transaction, with `FOR UPDATE SKIP LOCKED`.
  - **Dependencies:** `risk` never calls `transfer`. The `admin` module runs each review in one transaction: it calls `transfer` first, which takes the row lock, and then `risk` to record the review.
- **Rationale:** a hold through `reserved_balance` keeps the funds for the reviewer's decision without posting to the ledger. The reconciliation rule *available + reserved = ledger balance* (doc 01 §6.6) still holds.
- **Security implications:**
  - Risk scores, rule hits and review history are Internal data, visible only to staff.
  - Customers see only the transfer status; a rejected transfer shows a generic reason category, never rule details.
  - Cancelled held transfers still count toward the transfer-count rule, so submitting and cancelling cannot be used to probe the rules.
  - Every decision is audited.
- **History:** held, rejected, cancelled, expired and blocked transfers have no ledger entries. They appear in `GET /api/v1/transfers`, while the ledger-based `GET /api/v1/transactions` shows completed movements (doc 07 D06).
- **Values:** rule weights, decision thresholds and expiry were set by the owner on 2026-10-30 (doc 07 D27, D28). All of them are configuration.
- **Tests:**
  - band boundaries 39/40, 69/70 and 89/90;
  - a hold moves no money to the recipient and posts no ledger entries;
  - approve completes atomically from the reserved amount;
  - approve after the hold deadline is refused;
  - approve with a frozen or closed wallet ends `REJECTED` and releases the hold;
  - reject, cancel and expiry each release the hold and the limit;
  - approve racing cancel: exactly one wins;
  - neither the sender nor the recipient can review the transfer;
  - a block changes no balance;
  - review rows are append-only.

## 5. Verification approach
Unit and integration tests (Testcontainers PostgreSQL) are the primary evidence for wallet correctness: authorization, insufficient funds, duplicate requests, rollback, concurrent transfers and balance invariants. The CI smoke test only proves the stack starts and the main flow works; it is **not** evidence of financial correctness.
