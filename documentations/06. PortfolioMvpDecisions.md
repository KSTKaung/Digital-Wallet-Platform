## 1. MVP in one paragraph
One Spring Boot 4.1.2 application (Java 21) on port 8080, organised by business domain under `com.portfolio.wallet`, backed by one PostgreSQL database with one schema per domain. Domain boundaries are enforced by ArchUnit so modules can later be extracted into the eight documented services. A React + TypeScript + Vite SPA on port 5173 is the only client. Everything runs with free, open-source tools locally (Docker Compose) and on standard GitHub-hosted runners.

## 2. Decision log

Each entry: **Original** (target doc) · **MVP decision** · **Rationale** · **Security implications** · **Limitations** · **Tests**.

### MVP-ADR-01 Single modular application — Approved
- **Original:** 8 deployable microservices; "no modular monolith" (doc 01 ADR-001, ADR-002).
- **MVP decision:** one deployable with domain modules `auth`, `user`, `wallet`, `transfer`, `ledger`, `transaction`, `notification`, `audit`, `admin`, `common`. Modules talk only through each other's application services. Mapping to target services: auth → Identity; user → Customer & KYC; wallet → Wallet; transfer → Transfer; ledger → Ledger; notification → Risk & Notification (notification part); audit, admin → Admin & Operations.
- **Rationale:** a single developer, free tooling, and correctness over operational scale; extraction path preserved.
- **Security implications:** one process and one trust boundary; internal calls are in-process, so there are no internal network APIs to protect.
- **Limitations:** no independent scaling or deployment; one failure domain.
- **Amendment (owner, 2026-10-30):** a `risk` module is added for risk assessment and manual review (MVP-ADR-24); it maps to the risk part of Risk & Notification.
- **Tests:** ArchUnit module-boundary and no-cycle rules; layer rules per module.

### MVP-ADR-02 One database, schema per module — Approved
- **Original:** database per service, no cross-service joins or foreign keys (ADR-004).
- **MVP decision:** one PostgreSQL database, schemas `auth`, `usr`, `wallet`, `transfer`, `ledger`, `risk` (added 2026-10-30, MVP-ADR-24), `audit`, `notification`, one Flyway stream. No foreign keys or joins across schemas; a module's repositories touch only its own schema.
- **Rationale:** atomic money transactions without distributed coordination; boundaries kept for later split.
- **Security implications:** the ledger append-only rule is enforced by a trigger instead of separate role grants (see 03).
- **Amendment (owner, 2026-10-30; doc 07 D19):**
  - **Two database roles** replace the single application role:
    - a **migration owner**, which Flyway uses and which owns the schemas;
    - a **runtime role**, which the application uses, with DML only and no ownership.
  - The runtime role therefore cannot `ALTER TABLE … DISABLE TRIGGER`. This closes the trigger-bypass risk, for example through SQL injection.
  - The append-only triggers cover every table in the **append-only** list under "Database protections" below, each with a `BEFORE TRUNCATE` guard.
  - Both roles are standard PostgreSQL features; no new tool is needed.
- **Role provisioning (owner, 2026-10-30):**
  - Names: `wallet_owner` (migration owner, owns every schema) and `wallet_app` (runtime).
  - `wallet_app` is **not a superuser** and has no `CREATEROLE`; a superuser could bypass triggers through `session_replication_role`.
  - Roles are cluster objects, so an init script creates them before Flyway runs: the PostgreSQL init script in Compose, and the same script in Testcontainers. Flyway cannot create the role it runs as.
  - Credentials: two pairs from environment variables, one for the Spring datasource (`wallet_app`) and one for Flyway (`wallet_owner`).
  - Grants:
    - `GRANT USAGE` on each schema to `wallet_app`;
    - `ALTER DEFAULT PRIVILEGES`, so tables created by later migrations get their grants automatically;
    - DML on ordinary tables;
    - only `SELECT, INSERT` on the append-only tables, as defence in depth on top of the triggers.
- **Database protections (owner, 2026-10-30; PR 2 database review):**
  - **Append-only**, by triggers plus grants:
    - `ledger.ledger_entries` and `ledger.financial_transactions`;
    - `wallet.deposits` and `wallet.withdrawals`;
    - `risk.risk_assessments`, `risk.risk_rule_hits` and `risk.risk_reviews`;
    - `audit.audit_logs`.
  - **Never deleted**, but updatable:
    - `auth.users`, except that an account still `PENDING_VERIFICATION` is purged (a trigger refuses deleting any other, MVP-ADR-23);
    - `wallet.wallets` and `wallet.daily_limit_usage`;
    - `transfer.transfers`;
    - `ledger.ledger_accounts`, where only `status` may change;
    - `risk.investigations` and `risk.sender_risk_state`;
    - `usr.customers` and `usr.kyc_applications` (V8; `usr.customers` takes INSERT of `user_id` only);
    - `notification.notifications`, the email outbox, where only `status`, `attempts`, `next_attempt_at` and `last_failure` may change, and `SENT` and `FAILED` are final (V9, MVP-ADR-25).
  - **Transfers:** only a `PENDING_REVIEW` transfer may change, only to `COMPLETED`, `REJECTED`, `CANCELLED` or `EXPIRED`, and only in its status and decision fields. Every other state is final (doc 05 §4). Approve, reject and cancel are accepted only before `review_expires_at`; expire only at or after it. Both are measured when the UPDATE statement starts, so a decision that waited on locks past the deadline is refused and can expire the transfer in the same transaction (MVP-ADR-24). This holds only if the transfer row is locked by an earlier statement, as the lock order requires. The application supplies `review_expires_at` from configuration. Every stored transfer references its risk assessment.
  - **Ledger entries:**
    - an entry may only join a ledger transaction created in the **same database transaction**, so a posted transaction never gains entries. The database records the creating transaction's full 64-bit id (`created_xid`) and compares it exactly, together with `created_at`, so a transaction id reused after a logical restore does not match. A header not visible to the inserting transaction is refused;
    - entries on a `FROZEN` or `CLOSED` ledger account are rejected; customer accounts are read with `FOR SHARE`, so a concurrent freeze and a posting serialise. System and suspense accounts are not locked, which would make every deposit queue on one row; a posting in flight while one is frozen is accepted.
  - **Final states:** a `CLOSED` wallet or ledger account cannot change status; a `CLOSED` investigation cannot change at all and must name the closing officer and the outcome. An investigation is always inserted `OPEN`, with no closing fields, and keeps its `assessment_id` and `opened_at`. A transfer cannot be inserted in a review-final state (`REJECTED`, `CANCELLED`, `EXPIRED`), and has a rejection reason exactly when it is `REJECTED`. A `CLOSED` wallet's balance columns can still change, only so that a hold can be released; every other movement is refused by the domain and the ledger account.
  - **Wallets:** `id`, `wallet_number`, `customer_id`, `currency` and `created_at` never change.
  - **Ownership inside a schema:** deposits and withdrawals reference their wallet by `(wallet_id, customer_id)`; risk reviews reference their assessment by `(assessment_id, transfer_id)`, and a transfer has at most one review.
  - **Duplicates:** deposits and withdrawals store their `Idempotency-Key`, unique per customer, so a retry after the idempotency record is purged still cannot post twice.
  - **Timestamps:** the database sets `created_at` on ledger rows, ledger accounts, wallets, deposits, withdrawals, transfers and risk reviews, `held_at` and `decided_at` on transfers, `assessed_at` on risk assessments, `opened_at` and `closed_at` on investigations, `attempted_at` on lookup attempts (which the runtime role cannot update), and `occurred_at` on audit rows. The application cannot backdate them.
  - **Functions:** each trigger function runs with `search_path = pg_catalog, pg_temp`; new functions are not executable by `PUBLIC`.
  - **Driver:** `logServerErrorDetail` is off, so PostgreSQL error details (which can contain row values) are not logged.
  - **Risk band:** risk assessments store `decision` only, which maps one-to-one to the band.
- **Limitations:**
  - schemas share one instance;
  - the two credentials come from environment variables;
  - the backend container also holds the `wallet_owner` (Flyway) password, because migrations run at application startup. Accepted for the MVP (owner, 2026-10-30); a separate migration job is the production option;
  - the init script sends the role passwords inside `CREATE ROLE`, so a failing statement could write them to the PostgreSQL log. Accepted for local and test databases only (owner, 2026-10-30); production provisions roles outside the application;
  - the JDBC driver's `autosave` stays off (the default). The ledger guard no longer depends on it, but silent savepoint retries would hide errors in the money path. PR 4 adds a test.
- **Tests:** ArchUnit (repositories used only within their module); migration tests from an empty database; the runtime role cannot update or delete ledger or audit rows, or disable their triggers.

### MVP-ADR-03 Atomic ledger posting — Approved
- **Original:** ledger posted asynchronously from Kafka events; `ledgerStatus` `PENDING_POST/POSTED/FAILED_POST`; reconciliation; degraded mode above 50,000 THB (ADR-010, D-01, D-06, D-13).
- **MVP decision:** wallet snapshot updates, the balanced double-entry ledger transaction, the business record and its audit row are written in **one database transaction**. `ledgerStatus` is kept in money responses for contract compatibility and is `POSTED`, returned only after a successful commit; any failure rolls everything back and returns an error. Degraded mode does not apply. A scheduled reconciliation check logs any mismatch at ERROR level. It checks that:
  1. each wallet's `available_balance + reserved_balance` equals its ledger-derived balance (Σ CREDIT − Σ DEBIT);
  2. each `COMPLETED` deposit, withdrawal and transfer has exactly one ledger transaction;
  3. each wallet's `reserved_balance` equals the sum of its `PENDING_REVIEW` transfers;
  4. reserved daily-limit usage equals the same sum per limit date.

  (Amended 2026-10-30 for MVP-ADR-24.)
- **Rationale:** strongest consistency available without a broker; removes the posting-lag window.
- **Security implications:** ledger invariants (Σ DEBIT = Σ CREDIT, amount > 0, immutable entries, unique `transaction_reference`) still hold. Immutability is enforced by a PostgreSQL trigger rejecting `UPDATE`/`DELETE` on `ledger.ledger_entries` and `ledger.financial_transactions`.
- **Limitations:** ledger posting adds latency to the money path; `PENDING_POST` and `FAILED_POST` are never emitted.
- **Amendment (owner, 2026-10-30; doc 07 D09, revised the same day for MVP-ADR-24):**
  - The MVP transfer states are `COMPLETED`, `PENDING_REVIEW`, `REJECTED`, `CANCELLED`, `EXPIRED` and `BLOCKED` (MVP-ADR-24).
  - `PENDING` and `PROCESSING` (doc 02 §2.4) are never used.
  - Ledger entries are posted only when a transfer becomes `COMPLETED`, in the same transaction.
  - `POST /api/v1/transfers/{id}/cancel` is allowed only while the transfer is `PENDING_REVIEW`.
  - A transfer that fails validation (balance, limits, wallet status) leaves no transfer row; its audit row is written in its own transaction (doc 07 D08).
- **Tests:** rollback when ledger posting fails mid-transaction (no snapshot change, no record); balanced-entries invariant; UPDATE/DELETE on ledger rejected; reconciliation finds an injected mismatch.

### MVP-ADR-04 No internal network APIs or mTLS — Approved
- **Original:** mutual TLS and a per-caller allow-list on every service hop; `/internal/v1/**` APIs (ADR-011, D-07, D-09; doc 03 §3.6).
- **MVP decision:** internal APIs become in-process application-service calls. mTLS is **not implemented**; it is documented as a future requirement for a distributed deployment.
- **Rationale:** there is no service-to-service network traffic to authenticate.
- **Security implications:** threat T26 (rogue internal service) does not apply; T11 (internal API exposed) is replaced by "no `/internal/**` route exists".
- **Limitations:** must be revisited before any module is extracted.
- **Tests:** `/internal/**` returns 404.

### MVP-ADR-05 Gateway responsibilities inside the application — Approved
- **Original:** Spring Cloud Gateway does JWT validation, rate limiting, CORS, security headers and correlation ID (ADR-008, doc 03 §2.2).
- **MVP decision:** Spring Security (OAuth2 resource server, Nimbus JWT) plus application filters provide the same controls. The public URL contract `/api/v1/**` is unchanged.
- **Rationale:** no separate edge component is needed for one backend.
- **Security implications:** a single enforcement point remains, and `@PreAuthorize` plus ownership checks still apply.
- **Limitations:** no WAF or edge TLS locally; production needs HTTPS termination in front (see §4).
- **Tests:** 401 without/with expired/with tampered token; 403 by role; 404 for foreign resources; CORS preflight; correlation ID generated and echoed.

### MVP-ADR-06 PostgreSQL for idempotency and OTP; in-memory rate limiting — Approved
- **Original:** Redis for idempotency keys, rate-limit counters, OTP and the degraded-mode flag (doc 04 §3.4).
- **MVP decision:** `Idempotency-Key` records and hashed OTPs live in PostgreSQL. Rate limiting uses an in-memory, per-instance limiter with the documented limits (doc 02 §1.8: auth 10/min per IP, money POSTs 30/min per customer, others 300/min per user). OTP values are never logged.
- **Rationale:** no Redis; the DB unique constraint was already the final idempotency guard.
- **Security implications:** idempotency stays durable. The rate limiter is only correct for **one instance** and resets on restart.
- **Limitations:** a distributed rate limiter (Redis or edge) is required before running more than one instance.
- **Open question (owner, 2026-11-04, T4):** no maximum request body size is set; choosing one is an open question for a later hardening step (doc 07 D32).
- **Amendment (owner, 2026-10-30):** the wallet-lookup limits (MVP-ADR-20) and the OTP counters (MVP-ADR-23) are stored in **PostgreSQL**, so they hold across restarts and instances. All other limits stay in memory.
- **Tests:** idempotent replay returns the original response; same key + different body → `409 IDEMPOTENCY_KEY_REUSED`; concurrent duplicate requests produce one transfer; rate limit returns 429 with `Retry-After`; logs contain no OTP.

### MVP-ADR-07 Domain model purity — Approved (owner, 2026-10-30)
- **Original:** domain layer has no Spring/JPA/Kafka (ADR-003, doc 01 §3.4).
- **MVP decision:** the financial core (`wallet`, `transfer`, `ledger`, and `Money` in `common`) uses **pure domain models** with separate JPA entities and mappers in `persistence`. Supporting modules with little behaviour (`notification`, `audit`, user profile) use JPA entities directly; this is a documented compromise.
- **Rationale:** keeps the rules that guard money framework-free and unit-testable, without duplicating models where there is no domain logic.
- **Security implications:** none directly; it reduces the risk of persistence concerns leaking into balance rules.
- **Limitations:** mapper code in the financial modules.
- **Tests:** ArchUnit: `wallet|transfer|ledger..domain..` must not depend on `jakarta.persistence`, Spring or `..persistence..`; domain unit tests without Spring. The current domain rule does not yet forbid `jakarta.persistence` or Spring, so PR 2 extends it and adds a self-test (doc 07 D07).

### MVP-ADR-08 Locking — Approved
- **Original:** optimistic locking on `wallets.version`; two-wallet movements lock in ascending wallet-id order (ADR-009, doc 01 §6.8).
- **MVP decision:** keep the `version` column (optimistic check on every snapshot update) **and** take `SELECT … FOR UPDATE` row locks on both wallets in ascending id order inside the transfer transaction.
- **Rationale:** deterministic, deadlock-free behaviour under concurrent transfers in one database.
- **Security implications:** prevents lost updates and double spend (T5, T6); `CHECK (available_balance >= 0)` stays as the last guard.
- **Limitations:** serialises transfers touching the same wallet (acceptable at MVP scale).
- **Tests (PostgreSQL via Testcontainers):** N concurrent transfers from one wallet never overdraw; opposite-direction concurrent transfers do not deadlock; total money is conserved; ledger stays balanced.

### MVP-ADR-09 Packages and module names — Approved
- **Original:** `com.platform.<service>.{domain,application,infrastructure,presentation,config,security}`.
- **MVP decision:** `com.portfolio.wallet.<module>.{web,application,domain,persistence}`, created only where needed.
- **Tests:** ArchUnit layer rules.

### MVP-ADR-10 Minimal KYC before wallet creation — Approved
- **Original:** KYC with documents, face verification and compliance approval; wallet created on `KycApproved` (D-03, ADR-013).
- **MVP decision:** the rule is kept. A customer submits a minimal KYC application (level `BASIC` or `FULL`, document type and reference); an authorised reviewer approves or rejects it with a reason; approval creates the wallet with tier limits in the same transaction. Document upload and face verification are out of scope.
- **Security implications:** money endpoints return `403 KYC_REQUIRED` and `GET /wallet` returns `404 WALLET_NOT_FOUND` before approval; decisions are audited.
- **Limitations:** no identity evidence is actually verified.
- **Amendment (owner, 2026-11-03; PR 4 plan, doc 08 §4B):**
  - **What this is:** a basic KYC review workflow, **not identity verification**. Nothing checks that a document or name is real.
  - **Customer identity:** `customer_id` is the auth user id; `usr.customers` is keyed by `user_id` and created on the first profile or KYC call.
  - **Legal name:** `firstName` and `lastName`, at most 100 characters each, captured in the application, copied to the profile on approval and not editable afterwards. A legal-name change process is a possible future feature.
  - **Document:** type `ID_CARD` or `PASSPORT`; reference at most 50 characters. It is returned masked to everyone, staff included: the last 4 characters are visible only when at least 4 others stay hidden (8 characters or more); a shorter reference is masked whole (owner, 2026-11-03, K5). Masking is not encryption: field encryption stays a documented gap (MVP-ADR-12).
  - **Draft edit:** `PUT /api/v1/kyc/applications/{id}` changes a `DRAFT`. It is owner-only; another customer's id gives the identical `404`.
  - **Decisions:** only `COMPLIANCE_OFFICER`, through `/api/v1/admin/kyc/applications` (list by status, detail, approve, reject). The rejection reason (at most 500 characters) is shown to the customer; it is refused if it contains the application's own document reference, and staff are told not to include identity details.
  - **New error code** `INVALID_KYC_STATE` (409): submitting, editing or deciding an application in the wrong state.
  - **Freeze:** the customer freezes their own wallet; `ADMIN` freezes or unfreezes through `/api/v1/admin/customers/{id}/freeze|unfreeze` with a reason. The wallet and its ledger account change status **in one transaction**, wallet locked first, so a frozen wallet's ledger account refuses entries too. `suspend` and freezing a login are out of the MVP.
  - **Profile rules (owner, 2026-11-03):**
    - The document reference has no format rule beyond non-blank, at most 50 characters and no control or format characters (J6), so documents from any country fit.
    - `dateOfBirth` and `countryCode` are locked from submit onward (`PENDING_REVIEW` and `APPROVED`), so a reviewer never approves data that changed after they read it; `PUT /customers/me` then returns `409 INVALID_KYC_STATE`. A rejection unlocks them for correction, and the next submit locks them again. The lock comes from the database state of the applications, not a client flag. After approval, a correction would need its own workflow with compliance review, which is not in the MVP.
    - Submitting an application requires `dateOfBirth` and `countryCode` on the profile (`400 VALIDATION_ERROR`); creating and editing a draft do not. The database refuses such a submit too (J5), and the submit copies both onto the application (K4).
    - `dateOfBirth` must not be in the future (today counts, Asia/Bangkok). This is a validity check, **not** a minimum-age check.
    - **Concurrency (owner, 2026-11-04, N4):** "DOB and Country cannot be changed after submission, enforced even when multiple requests occur concurrently." The profile update, the submit and the approval run at READ COMMITTED (set explicitly) and serialise on the profile row lock (`FOR NO KEY UPDATE` against the submit trigger's `FOR SHARE`); the trigger re-reads the applications after the wait, so an update queued behind a submit is refused, and a submit queued behind an update submits the updated values.
    - **Approval and legal name (owner, 2026-11-04, N3):** a deferred constraint trigger checks at commit that an application which became `APPROVED` has its legal name on the profile, so an approval that skipped the copy rolls back whole.
  - **Open question before production (owner, 2026-11-03):** the **minimum age** must be set from the law and financial regulation of each country served. It is not defined in the MVP, and must be decided with legal and business input before production.
  - **After approval (owner, 2026-11-04, P6):** the legal name, the date of birth and the country stay locked. A correction workflow, with compliance review, is future work and an open item; until it exists, a wrong approved value cannot be corrected in the MVP.
  - **Duplicate document references (owner, 2026-11-04, P5):** the same document reference may be used by two customers; nothing refuses it. Allowing it does **not** mean that duplicate identities are accepted as verified: the MVP KYC is a review workflow, not identity verification (see "What this is" above). Detecting duplicates across customers is an open item.
  - **Masking on the profile:** email as first character, `***`, then the domain (`a***@example.com`); phone with only the last 4 digits visible.
  - **Staff review (owner, 2026-11-03):**
    - Drafts are invisible to staff: list, detail and decisions on a `DRAFT` give the identical `404`; the list shows `PENDING_REVIEW` by default.
    - Approve and reject return `200` with the staff detail view. The reviewer sees the full legal name and the date of birth and country **copied onto the application at submit**, never the current profile, so a profile corrected after a rejection does not change what a past decision was based on (owner, 2026-11-03, K4). The document reference stays masked.
    - The queue is ordered by submission time, **oldest first**, then by id, so applications are worked in the order customers submitted them; a matching index leaves drafts out (K3; owner, 2026-11-04, P2).
    - A rejection reason is refused if it contains the document reference, compared after Unicode NFKC normalisation, lower case, and removing everything but letters and digits. A very short reference can refuse an unrelated reason; staff then reword it. The check **catches accidental inclusion, not deliberate evasion**: a reviewer who writes the reference in Thai digits, look-alike letters from another script or spelled-out words gets past it (owner accepted, 2026-11-03, K6). Staff guidance and the audit trail cover the deliberate case.
    - Reasons (rejection, freeze, unfreeze) also refuse format characters (zero-width characters, bidirectional marks) and must contain at least one letter or digit; free-text KYC fields refuse format characters too, with one exception: the legal name (`firstName`, `lastName`) accepts zero-width non-joiner U+200C and joiner U+200D, which names in Persian, several Indic scripts and others need to be spelled correctly (owner, 2026-11-04, P1), but only between two letters or combining marks, never at the start or end and never next to another joiner; a legal name must also contain at least one letter, counted over Unicode code points, so the masked initial of the last name (its first letter) is always a letter (R2). Every other format character and every other field stays refused. Errors name the field, never the value (J6). **Accepted limit (owner, 2026-11-04, S4):** a joiner between two Latin letters is allowed and renders the same as the name without it, so two stored names can look identical and differ; the MVP has no name matching or deduplication, so nothing relies on two names comparing equal. The request layer and the domain apply the same rule, also to letters outside the Basic Multilingual Plane (S3).
    - The customer's email says a decision was made and when (K2); the reason is shown only after signing in.
  - **Wallet creation:** the wallet number is drawn up to **5 times** (configuration, MVP value) if it collides. If every attempt collides, the approval fails with `500 SYSTEM_ERROR` and nothing is created; the application stays `PENDING_REVIEW`.
  - **Access rules:** one ordered table in `SecurityConfig`, least privilege per group: `/api/v1/admin/kyc/**` `COMPLIANCE_OFFICER`; `/api/v1/admin/customers/**` `ADMIN`; any other `/api/v1/admin/**` denied; `/customers/**`, `/kyc/**`, `/wallet/**`, `/wallets/**` `CUSTOMER`; `logout` and `change-password` any signed-in user; **any other `/api/v1/**` path `CUSTOMER`** (J3), so a new endpoint without its own rule is closed to staff. Each role rule applies only to a request that reaches an endpoint: a path with no handler is the generic `404` for every signed-in caller, never a `403` that would reveal which paths exist, and a wrong method on a known path is `403` for the wrong role (MVP-ADR-19). An unauthenticated request gets the identical `401` on every path. Controllers keep `@PreAuthorize` as a second layer, and ownership is checked in the services. Another customer's resource stays the identical `404` (MVP-ADR-19).
  - **Freeze:** repeating a freeze or unfreeze returns `200` with the current status and changes nothing (no audit row). The customer has no unfreeze endpoint. Freeze or unfreeze of a `CLOSED` wallet returns `500`, because `CLOSED` cannot be reached.
  - **Freeze emails (owner, 2026-11-03):** when staff freeze or unfreeze a wallet and the status actually changes, the customer is emailed, with no reason, balance or wallet number, and with the time of the change (K2). The email is an outbox row written in the change's transaction and sent after commit (MVP-ADR-25): nothing is sent on rollback or on a repeated request, and of concurrent requests only the one that changed the status writes a row. A failed lookup or send is retried (5 attempts) and never undoes the change. A self-freeze sends nothing.
  - **Deposit and withdrawal responses (PR 4b):** they show `walletNumber`, not the internal wallet id.
  - **Persistence:** JdbcClient, not JPA, with the `version` check in SQL, so database-set columns can never be written by mistake.
- **Tests:** no wallet before approval; one wallet per customer; rejection needs a reason; re-application after rejection; reviewer cannot approve their own application.

### MVP-ADR-11 Unified transaction history — Approved
- **Original:** per-service lists in MVP; unified `/transactions` API is Backlog (doc 02 §8).
- **MVP decision:** the read-only `transaction` module exposes `GET /api/v1/transactions` (paged, owner-only) over deposits, withdrawals and transfers.
- **Tests:** a customer sees only their own entries (404/empty for others); paging bounds 1–100.

### MVP-ADR-12 Scope reductions — Approved (owner, 2026-11-03)
Out of scope for this MVP and documented as Backlog: merchant/QR payments and refunds, linked cards, bill payment and top-up, beneficiaries, MFA, devices, SMS/push, settlement.
Requirements that touch security or financial integrity are **not dropped silently**. The proposed handling, which needs approval:

| Target requirement | Proposed MVP handling |
| ------------------ | --------------------- |
| Risk evaluation before money movement; `BLOCK` changes no balance (doc 05 F-RISK) | **superseded by MVP-ADR-24** (owner, 2026-10-30): scored assessment with four bands, manual review and blocking |
| Maker-checker for sensitive admin actions (doc 03 §3.5) | no MVP admin action needs it: no limit changes, no Premium tier, no manual adjustments. Unfreeze requires a reason and is audited |
| Step-up authentication above a threshold (BR-009) | not implemented; documented gap |

### MVP-ADR-14 Refresh token transport — Approved (owner, 2026-11-02)
- **Original:** login/refresh return `refreshToken` in the JSON body; the SPA must not store it in `localStorage` (doc 02 §2.1, §7).
- **MVP decision:** the refresh token is set as a cookie: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`, rotated on every use and **not** returned in the body. The access token stays in the body and in SPA memory. The SPA reaches the API **same-origin** (Vite dev proxy and nginx in Compose forward `/api` to :8080), so no credentialed CORS is needed. CSRF on cookie-authenticated endpoints (`/auth/refresh`, `/auth/logout`) is mitigated by `SameSite=Strict` plus a required `X-Requested-With` header and an `Origin` allow-list check. Fallback if this proves impractical: memory-only tokens, with reload requiring login.
- **Rationale:** survives page reload without exposing the refresh token to JavaScript.
- **Security implications:** XSS can no longer read the refresh token; refresh-reuse detection revokes the token family (doc 03 §3.4).
- **Limitations:** an **API contract change** to doc 02 §2.1 (no `refreshToken` in the body). Browsers treat `http://localhost` as a secure context, so `Secure` cookies work locally.
- **Tests:** the cookie has the required attributes; refresh without the header or from a foreign Origin → 403; refresh rotation; reuse of a rotated token revokes the family; logout clears the cookie.

### MVP-ADR-20 Recipient discovery by wallet number — Approved (owner, 2026-10-30)
- **Original:** `POST /api/v1/transfers` takes `receiverCustomerId` (doc 02 §2.4), and no lookup is documented. Beneficiaries are out of scope (MVP-ADR-12).
- **MVP decision:**
  - **Wallet number:** every wallet has a public wallet number, separate from its internal UUID.
    - It is unique, **immutable** (a database trigger rejects changes), random and non-sequential, with a check digit.
    - The exact format is fixed in the PR 4 plan. "Wallet ID" in the owner's decision means this number.
    - It has at least 10 random digits plus the check digit (owner, 2026-10-30).
  - **Lookup:** `GET /api/v1/wallets/lookup?walletNumber=…` does an **exact** match only.

  - A lookup confirms that a wallet number exists. This is accepted for usability and mitigated as follows:

    - only KYC-approved callers with an `ACTIVE` wallet can look up;

  - **10 lookups per minute per authenticated user** and **30 per minute per client IP**, as sliding windows stored in PostgreSQL.
  - Successful and unsuccessful lookups both count.
  - When exceeded: `429` with `Retry-After`.
  - Enforced in the backend only.
  - The client IP comes from `X-Forwarded-For`, trusted only when set by the nginx proxy.
- **Tests:**
  - exact match only;
  - masked fields;
  - identical `404` for every non-eligible case;
  - rate limit;
  - audit row;
  - the wallet number cannot be updated;
  - a transfer to a looked-up wallet number.

### MVP-ADR-21 Money precision — Approved (owner, 2026-10-30)
- **Original:** `NUMERIC(19,4)` (doc 01 §7.4); JSON money with at most 4 decimals (doc 02 §1.6).
- **MVP decision:**
  - Every THB amount and balance is `NUMERIC(19,2)` in PostgreSQL and `BigDecimal` with scale 2 in Java.
  - A request with **more than two decimal places is rejected** with `400 INVALID_AMOUNT`, never rounded. The rule is value-based (owner, 2026-10-30): a non-zero digit after the second decimal is rejected (`1.001`), while trailing zeros lose nothing and are accepted (`1.0000` = `1.00`).
  - `float` and `double` are never used for money.
  - Currency is always explicit, as an ISO 4217 code (`char(3)`, `THB` only).
- **Rationale:** THB has two minor units; storing more precision invites rounding differences between snapshot and ledger.
- **Limitations:** a currency with three minor units would need a migration and a new ADR.
- **Enforcement:** PostgreSQL rounds a value to `NUMERIC(19,2)` on assignment, so the database cannot reject extra decimals. The rule is therefore enforced in the API and domain layers: `Money` uses `setScale(2, RoundingMode.UNNECESSARY)`. A test proves that a scale-3 value never reaches a repository.
- **Tests:** 2 decimals accepted; 3 rejected; amounts compared with `compareTo`, not `equals`; the database rejects nothing that the API accepts.

### MVP-ADR-23 Authentication parameters and password hashing — Approved (owner, 2026-10-30)
- **Original:** "strong policy", lock after 5 failures, OTP 5 minutes and 5 attempts, BCrypt (doc 03 §3.4, doc 06 §4).
- **MVP decision**, all values configuration:

  | Item | Value |
  | ---- | ----- |
  | Lockout | after **5 consecutive** failed logins, for **15 minutes**; the counter resets on a successful login. It is tracked per identifier, unknown emails included. A successful **password reset clears the lock**, and the account owner is **emailed** when the lock starts. Counters for unknown emails live in their own table and are deleted after 24 hours. The limit of 10 requests per minute per IP on `/auth/**` stays (doc 02 §1.8) |
  | Password | **12–128 characters**; may not repeat any of the **last 5** passwords |
  | Password hashing | **Argon2id** (Spring Security `Argon2PasswordEncoder` with Bouncy Castle, a free dependency approved by the owner and added in PR 3). This replaces BCrypt, whose 72-byte input limit cannot hold a 128-character password. Cost parameters are configuration, defaulting to the OWASP baseline: memory 19 MiB, 2 iterations, parallelism 1. The number of hashes computed at the same time is bounded. Unknown and locked accounts still run a dummy hash, so all login failures take the same time. Length is counted in Unicode code points after NFC normalisation |
  | OTP | **6 digits**; valid **5 minutes**; at most **5 verification attempts** per challenge; resend cooldown **60 seconds**; at most **5 resends per hour**. A resend cancels the previous code. After **5 used-up challenges within 24 hours** the identifier gets no new challenge until the 24-hour window clears. `resend-otp` and `forgot-password` always return `202`, also for unknown identifiers |
  | OTP storage | keyed hash (HMAC-SHA256); the secret comes only from an environment variable. Resend and attempt counts are stored in PostgreSQL, so they survive a restart (MVP-ADR-06) |

  Passwords and OTPs are never stored, logged or returned in plain text.
- **Login response:** a wrong password, an unknown account and a locked account return the **same** `401`, so the response does not reveal whether an account exists. This changes doc 02 §2.1, which returned `403 ACCOUNT_LOCKED`. The lock is still audited.
- **Amendment (owner, 2026-11-02; PR 3 plan, doc 08 §4A):**
  - **Registration does not reveal existing accounts.** It always returns the same `201` with `{email, status: PENDING_VERIFICATION}` and no user id, replacing doc 02's `409`. Argon2id always runs. If the email is taken, its owner gets a notice email; if only the phone is taken, the phone's owner does.
  - **`verify-otp` failures are identical.** Wrong, expired, used-up and unknown all return `400 INVALID_OTP`. The limits still apply, and the audit row records the real reason and the keyed identifier hash, never the email or the code. Success for `REGISTRATION` returns an empty `200`. `OTP_EXPIRED` and `OTP_ATTEMPTS_EXCEEDED` stay in the enum, unused.
  - **`resend-otp` always returns `202`.** A cooldown or cap silently sends nothing; only the per-IP limiter can return `429`. A malformed body still returns `400`, which says nothing about any account.
  - **Password reset:** `forgot-password` sends an OTP; `verify-otp` with `PASSWORD_RESET` returns `{resetToken}`; `reset-password` uses it. The token is valid **15 minutes**, single-use and stored as a hash. A reset revokes all sessions and clears the lock. `purpose: LOGIN` is refused, because MFA is Backlog.
  - **Sessions:** a `sessions` row and a `sid` JWT claim. Each request is rejected if its session is revoked or idle for 30 minutes, or its user is not `ACTIVE`, so logout, freeze and password change take effect at once. `last_seen_at` is written at most once a minute. A session idle for 30 minutes ends. A session also ends at most **7 days after login**, however active it is: a rotated refresh token inherits the earlier expiry, and an access token never outlives that cap.
  - **User status:** `PENDING_VERIFICATION`, `ACTIVE`, `FROZEN`, `SUSPENDED`. Anything but `ACTIVE` gets the same login `401`.
  - **Staff accounts:** there are no staff-management endpoints. A startup runner creates an `ADMIN` and a `COMPLIANCE_OFFICER` from optional environment variables, only if set and absent. Migrations seed no accounts.
  - **Secrets:** `JWT_PRIVATE_KEY`, `JWT_KID`, `OTP_HMAC_SECRET` and `REFRESH_TOKEN_PEPPER` are required in every profile; startup fails without them. One active signing key; rotation stays a target (§4).
  - **Email:** `spring-boot-starter-mail` is approved (free). Mailpit starts by default in Compose. Mail is sent after commit and asynchronously; a send failure is logged and audited, and does not fail the request.
  - **Phone format:** E.164 pattern only (`+` and 8–15 digits).
  - **Hashing values:** at most **4** password hashes at once, dummy hashes included. Argon2 salt 16 bytes and hash 32 bytes (Spring's defaults).
  - **Mail values:** SMTP timeouts of 5 seconds; the sender defaults to `no-reply@wallet.local` (`MAIL_FROM`).
  - **Malformed requests:** a missing query parameter or cookie and a failed method validation return `400 VALIDATION_ERROR`, naming the field and never the value. `/auth/refresh` without its cookie still returns the generic `401`. A foreign `Origin` on `/api/**` returns `403` in the documented error body.
  - **Change-password:** a wrong current password returns the generic `401` and is audited, but does not count towards the lockout, so a stolen access token cannot lock out its owner.
  - **Client IP:** Tomcat believes `X-Forwarded-For` only from `TRUSTED_PROXIES` (empty by default). Compose fixes the subnet `172.30.0.0/24` so the backend trusts exactly nginx's address, and nginx overwrites the header.
  - **Token issuer:** `app.jwt.issuer` (`JWT_ISSUER`, optional), default `wallet`.
  - **Unverified accounts (owner, 2026-11-02; PR 3 security review):** a code alone never activates an account. `verify-otp` for `REGISTRATION` also requires the password, so an attacker who registers a victim's email first cannot end up with a working password on it. Registering again on an unverified account replaces its password and phone and cancels the old code. Unverified accounts are purged after **24 hours**.
  - **OTP guesses:** the 24-hour block also starts at 25 wrong guesses per identifier in the window (5 used-up challenges × 5 attempts), so cancelling a code before its 5th guess does not avoid it.
  - **Password change:** it invalidates unused reset tokens and cancels the live reset code.
  - **Owner notices:** at most one per owner per hour.
  - **Rate-limit key:** the full IPv4 address, or the /64 prefix for IPv6.
  - **Lock email and audit:** the lock email goes only to `ACTIVE` accounts; other accounts still count towards the lock. Refusals are audited as `ACCESS_DENIED` and `CSRF_REFUSED`; a `401` and a foreign `Origin` are logged only. A refused refresh and a reuse revocation record no actor and name the token's owner in `new_value.ownerId`, so a thief's replay does not show the victim as having acted.
  - **Open risks (owner, 2026-11-02; each stays open until its condition is met):**
    - **Phone squatting:** an attacker can hold a victim's phone on an unverified account and re-register it every 24 hours, blocking that number indefinitely. **Open until phone verification exists.**
    - **Limiter table full:** at 100,000 tracked keys, new clients get `429` on `/auth/**` for up to a minute; the alternative would let an attacker reset their own count. **Open until the limiter's capacity is increased.**
    - **Audit volume for `403`:** re-assessed in PR 4 (owner, 2026-11-03). At most one `ACCESS_DENIED` row per user per minute, in memory, with the rest logged. **Closed for the MVP**, except that the cap resets on restart and holds per instance, and that at most 100,000 users are tracked (an MVP value; while full, further refusals are logged only); a shared limiter (for example Redis) is the target for more than one instance.
  - **Accepted trade-offs:** anyone can re-register an unverified email, which cancels the owner's code, so a repeating attacker can delay verification but not take the account. Anyone can burn a victim's OTP limits, blocking their code or reset for up to 24 hours. Registering with a target's phone reveals whether it is taken, because the registrant's own inbox gets no code; closing this needs phone verification. Logout with an expired access token returns `401` and keeps the cookie, so the client refreshes first.
  - **Documented gap:** the breached-password check (doc 03 §4.2 T1) is not implemented.
- **Tests:**
  - lockout at the 5th consecutive failure and expiry after 15 minutes (fixed clock);
  - a success resets the counter;
  - password lengths 11, 12, 128 and 129;
  - reuse of each of the last 5 passwords rejected;
  - OTP expiry, attempt limit, cooldown and hourly cap;
  - hashes only in the database;
  - no OTP or password in the logs.

### MVP-ADR-24 Risk assessment and manual review — Approved (owner, 2026-10-30)
- **Original:** risk evaluation returns `ALLOW | REVIEW | BLOCK` (doc 02 §4.4); a block never changes balances (doc 05 §4); MVP-ADR-12 proposed a single threshold rule.
- **MVP decision:**
  - **Module:** a separate `risk` module and schema (amends MVP-ADR-01 and -02).
    - Tables: `risk_assessments` (score, band, decision, time), `risk_rule_hits` (rules triggered), `risk_reviews` (reviewer, decision, reason, time; append-only) and `investigations` (assessment, status `OPEN`/`CLOSED`, closing officer, outcome).
    - The assessment is recorded in its own transaction before any money moves.
    - **If the evaluation fails, the transfer is rejected** with `SYSTEM_ERROR`: no transfer row, no hold, no funds moved, and an audit row is written. A failed evaluation never counts as score 0.
    - Assessments of the same sender are serialised by a per-sender row lock in the `risk` schema, so concurrent requests cannot bypass the transfer-count rule.
  - **Score:** 0–100, the sum of the rule weights, capped at 100. Weights and thresholds are configuration (owner, 2026-10-30; doc 07 D27):

    | Rule | Condition | Weight |
    | ---- | --------- | ------ |
    | Transfer amount | 10,000.01–25,000.00 THB | +10 |
    | | 25,000.01–40,000.00 THB | +20 |
    | | above 40,000.00 THB | +30 |
    | Transfer frequency | 3–4 transfers within 10 minutes | +15 |
    | | 5–7 transfers within 10 minutes | +25 |
    | | 8 or more transfers within 10 minutes | +35 |
    | New recipient | first successful transfer from this sender to this recipient | +15 |
    | New wallet (sender's) | less than 24 hours old | +20 |
    | | 24 hours to less than 7 days old | +10 |

    - Only the **highest matching weight per rule** applies.
    - **Transfer frequency** counts the sender's assessed transfers in the last 10 minutes, including the current one and all outcomes (blocked and cancelled too).
    - The `transfer` module passes the facts the rules need (amount, sender wallet age, whether a completed transfer to this recipient exists). The frequency count comes from the `risk` schema's own assessments.
    - The triggered rules and each rule's score are stored in `risk_rule_hits`.
  - **Bands** (boundaries are configuration):

    | Score | Decision | Effect |
    | ----- | -------- | ------ |
    | 0–39 | `ALLOW` | normal atomic transfer (MVP-ADR-03) |
    | 40–69 | `MONITOR` | normal transfer, assessment flagged for monitoring |
    | 70–89 | `MANUAL_REVIEW` | transfer `PENDING_REVIEW`; **no money reaches the recipient** |
    | 90–100 | `BLOCK` | transfer `BLOCKED` (the row is kept), `403 RISK_BLOCKED`; no balance changes; an investigation is opened in `risk.investigations`; the wallet is not frozen automatically |

  - **Hold:** in one transaction, the amount moves from the sender's `available_balance` to `reserved_balance` (no ledger entries), and the daily limit is reserved on the submission day (MVP-ADR-22).
  - **Review:** by a `COMPLIANCE_OFFICER` (MVP-ADR-12), who may be **neither the sender nor the recipient**. Both are compared by the auth user id behind each wallet.
    - **Approve:** one transaction checks that the hold has not expired, re-checks the wallets, captures the reserved amount, credits the recipient, posts the ledger and sets `COMPLETED`.
    - If the sender or recipient wallet is frozen or closed at that moment, the transfer becomes `REJECTED` instead, and the hold is released.
    - **Reject:** `REJECTED`, and the hold and the limit are released.
  - **Cancel:** the sender may cancel while the transfer is `PENDING_REVIEW` and the hold has not expired (`CANCELLED`), even if the sender wallet is frozen. Cancelling releases the hold and the limit.
  - **Expiry (owner, 2026-10-30; doc 07 D28):**
    - A transfer may stay in `PENDING_REVIEW` for at most **24 hours**, counted from when it entered that state (UTC timestamps).
    - After **12 hours**, compliance officers are notified that it will expire.
    - No extension exists in the MVP.
    - At 24 hours it becomes `EXPIRED`: neither wallet is debited or credited, the reserved funds and the daily-limit capacity are released, and the expiry is audited.
    - Expiry is processed by a scheduled job, and is also checked during every admin action. An approve or reject that finds the deadline passed expires the transfer in the same transaction and returns `409 INVALID_TRANSFER_STATE`.
    - The job interval is configuration.
  - **Concurrency:** approve, reject, cancel and expire each run in one transaction, which also writes the `risk_reviews` row, so no review row exists for an action that lost.
    - Lock order: the transfer row `FOR UPDATE`, then the wallets in ascending id order in one SQL statement, then the limit-usage rows.
    - The first action wins; the others get `409 INVALID_TRANSFER_STATE`.
    - The expiry job handles one transfer per transaction, with `FOR UPDATE SKIP LOCKED`.
  - **Dependencies:** `risk` never calls `transfer`. The `admin` module runs each review in one transaction: it calls `transfer` first, which takes the row lock, and then `risk` to record the review.
- **Rationale:** a hold through `reserved_balance` keeps the funds for the reviewer's decision without posting to the ledger. The reconciliation rule *available + reserved = ledger balance* (doc 01 §6.6) still holds.
- **Security implications:**
  - Risk scores, rule hits and review history are Internal data, visible only to staff.
  - Customers see only the transfer status; a rejected transfer shows a generic reason category, never rule details.
  - Cancelled held transfers still count toward the transfer-count rule, so submitting and cancelling cannot be used to probe the rules.
  - Every decision is audited.
- **History:** held, rejected, cancelled, expired and blocked transfers have no ledger entries. They appear in `GET /api/v1/transfers`, while the ledger-based `GET /api/v1/transactions` shows completed movements (doc 07 D06).
- **Values:** rule weights, decision thresholds and expiry were set by the owner on 2026-10-30 (doc 07 D27, D28). All of them are configuration.
- **Tests:**
  - band boundaries 39/40, 69/70 and 89/90;
  - a hold moves no money to the recipient and posts no ledger entries;
  - approve completes atomically from the reserved amount;
  - approve after the hold deadline is refused;
  - approve with a frozen or closed wallet ends `REJECTED` and releases the hold;
  - reject, cancel and expiry each release the hold and the limit;
  - approve racing cancel: exactly one wins;
  - neither the sender nor the recipient can review the transfer;
  - a block changes no balance;
  - review rows are append-only.

### MVP-ADR-25 Email outbox for business notifications — Approved (owner, 2026-11-03)
- **Original:** notifications are consumed from Kafka events (doc 01); MVP-ADR-03 and doc 07 exclude `outbox_events` and `processed_events`. PR 3 and PR 4a sent emails after commit on a virtual thread, with no retry and no record.
- **MVP decision:** business emails (KYC decisions, wallet freeze and unfreeze, and later money emails) go through an **email outbox in PostgreSQL**. There is no Kafka and no new dependency.
  - **Table:** `notification.notifications` (doc 01 §7.2). Each row has a stable, unique **event id** (UUID), the recipient's user id, the email kind, the template values (never KYC content, secrets or the email address), the time of the change, a status `PENDING` → `SENT` | `FAILED`, the attempt count and the next attempt time.
  - **Written in the business transaction:** the row commits or rolls back with the change it reports. A rolled-back change sends nothing.
  - **Address looked up at send time,** through one port in `notification.application` implemented by `auth`. No money module holds an email address, and no lookup runs while money locks are held.
  - **Dispatch (owner, 2026-11-04, N1, R1):** an in-process scheduled job handles each row in three steps, so no step holds a transaction while it waits on SMTP and no failing row holds back the others:
    1. **Claim**, in a short transaction: the oldest due `PENDING` row with fewer than the maximum number of attempts is locked with `FOR UPDATE SKIP LOCKED`; the claim **adds one to `attempts`** and moves the next attempt time forward by a **lease** (configuration, 5 minutes, not a documented value), and the transaction commits. Each claim has its own number: the new attempt count is the claim's **fencing token**. Until the lease ends no other run claims the row, and **there is never a claim beyond the maximum** (no 6th claim).
    2. **Send**, with no transaction open: resolve the kind, look up the address and hand the message to SMTP. Any failure here fails this attempt: an unknown kind (recorded as `UnknownKind` and retried, so a redeploy that knows it again still delivers it), a missing address, a database error in the lookup, or an SMTP error. The recorded failure is the exception's class name, cut to the column size.
    3. **Record**, in a short transaction: `SENT`; or, after a failure, the next attempt time by the backoff (the attempt count stays the claim's), or `FAILED` if this was the last claim. Every result is conditional on `PENDING` and on the fencing token, so **a result from an older claim is ignored** (logged, nothing recorded): a worker whose lease ended while it was still sending cannot overwrite the result of the newer claim, nor shorten its lease.
    - **The last (5th) claim** stays `PENDING` while it sends. If the send succeeds the row becomes `SENT`; if it fails, `FAILED`. If its lease ends without a result (a crash, or a result that could not be recorded), the start of the next run marks the row `FAILED` with `LeaseExpired` (logged with event id and kind only). So a row that keeps crashing ends `FAILED` after 5 claims instead of being claimed forever.
    - A failure on one row never stops the run: the next row is handled, up to the batch size. Only a failing statement of the run itself (the database is unavailable) ends it early.
    - Delivery is **at least once**, never exactly once; the state transitions are idempotent. A `SENT` or `FAILED` row is final and never sent again.
  - **Lease check at startup (owner, 2026-11-04, R3, S1):** the application does not start unless the lease is strictly longer than one send can take: connection timeout + **8 × read timeout** (the server replies of one send: EHLO, STARTTLS or the TLS handshake, MAIL FROM, RCPT TO, DATA, end of data, QUIT, and one as a margin) + write timeout + the address lookup timeout (T2), plus a **safety margin of 30 seconds** (`app.notification.outbox.lease-safety-margin`, MVP value). With today's 5-second timeouts that is 5 + 40 + 5 + 5 + 30 = 85 seconds, well below the 5-minute lease. The sum is computed without overflow, and an SMTP timeout above 2,147,483,647 ms (an int, which JavaMail would ignore, meaning no timeout) fails startup (T1). The timeouts are read for the configured protocol: `mail.smtp.*` for `smtp` (the default) and `mail.smtps.*` for `smtps`; a missing, zero or non-numeric timeout fails, any other protocol fails, and a JNDI mail session (`spring.mail.jndi-name`) fails, because its timeouts are not in this configuration. The address lookup of each send has its own statement timeout (`app.notification.outbox.address-lookup-timeout`, **5 seconds**, MVP value, a per-statement JDBC query timeout because the lookup runs with no transaction open); a timeout fails that attempt. The check keeps an ordinary send inside its lease. It does not make a slow or paused worker safe on its own; the fencing token of R1 does.
  - **Clock (owner, 2026-11-04, N2):** every time the dispatcher compares or writes (the due time on enqueue, the lease, the backoff) comes from the application clock. The time of the change (`occurred_at`) stays the database's `now()` of the business transaction, because it must equal the change's own database stamps, such as the KYC `decided_at`.
  - **Retry (MVP values, configuration):** at most **5 attempts** (claims), retried after about 1, 5, 15 and 60 minutes. Address-lookup failures follow the same policy. After the last attempt the row is `FAILED`, logged with the event id and kind (no address), and is not retried automatically.
  - **Failure never undoes the change:** dispatch runs after commit, in its own transactions. A failed lookup or delivery only updates the outbox row.
  - **Retention:** `SENT` and `FAILED` rows are kept; no purge in the MVP. **Open question (owner, 2026-11-04, P4):** how long outbox rows are kept, to be decided before PR 5.
  - **Not covered:** OTP, registration and password-reset emails in `auth` stay direct (time-limited codes, and a user who doesn't get one asks again).
- **Limits (documented, accepted):**
  - SMTP has no exactly-once delivery, and neither has the outbox: delivery is at least once. If the process stops, or recording the result fails, after the SMTP server accepted a message, the row stays `PENDING` and is claimed again when its lease ends (if claims remain): that one email is sent again. A send that takes longer than the lease can also overlap a newer claim of the same row; the fencing token then keeps the older result from being recorded, but both sends may reach the customer.
  - Delivery order is not guaranteed. Each email states the time of the change, which explains the order to the reader but does not enforce it (for example, "unfrozen" may arrive before "frozen").
  - The job runs per instance; `SKIP LOCKED`, the lease and the fencing token keep it correct with more than one.
- **Rationale:** the owner required a stable event id; that a result from an older claim is ignored and a processed email (`SENT` or `FAILED`) is never claimed again, with delivery at least once (see Limits); a retry and failure policy; and that a failed email never undoes a committed wallet or money transaction (owner, 2026-11-03).
- **Tests:** the row commits and rolls back with the change; a second claim of the same row sends nothing; a stale worker's result is ignored after the row was claimed again (the row stays `SENT`); the 5th claim may succeed (`SENT`), its failure or its expired lease make the row `FAILED`, and there is no 6th claim; a crash loop ends `FAILED` after 5 claims; the application does not start with a lease shorter than the mail timeouts plus the margin; a leased row cannot be claimed again until the lease ends; a failed `SENT` record leads to one re-send after the lease; a database error in the lookup, an unknown kind and an over-long failure name each count an attempt and do not hold back the next row; concurrent dispatch within the lease sends each row once; a lookup or SMTP failure retries on the schedule and ends `FAILED` after 5 attempts; a failure leaves the business change committed; no address or KYC content is stored or logged.

## 5. Verification approach
Unit and integration tests (Testcontainers PostgreSQL) are the primary evidence for wallet correctness: authorization, insufficient funds, duplicate requests, rollback, concurrent transfers and balance invariants. The CI smoke test only proves the stack starts and the main flow works; it is **not** evidence of financial correctness.
