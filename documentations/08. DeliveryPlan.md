## 2. Planning and delivery procedure
Every PR follows the same steps (CLAUDE.md, `.claude/WORKFLOW.md`):
1. **Plan:**
   - the `plan-feature` skill produces requirements with doc references, affected components, risks, acceptance criteria, test cases, an implementation sequence and open questions;
   - nothing is changed while planning.
2. **Decide:**
   - the owner answers the open questions;
   - decisions that change an MVP rule go into doc 06 (and doc 07 for data), never only into a plan.
3. **Accept:** the owner accepts the plan, and **it is recorded in this file** (§4 onwards).
4. **Implement** in small steps, using the agent and skill named for each step:
   - `backend-engineer`, `frontend-engineer` and `test-engineer`;
   - the skills `database-migration`, `implement-rest-api`, `secure-wallet-transfer` and `testing-workflow`.
5. **Review:**
   - `code-reviewer`, plus `security-reviewer` and/or `database-reviewer` where the workflow gates require them;
   - the main session checks each finding against the code and reports it as confirmed or dismissed.
6. **Verify:**
   - `./mvnw verify`, the frontend checks and a Compose check, as relevant;
   - only results of commands that actually ran are reported.
7. **Deliver:**
   - commit, push, PR and merge, **each only with the owner's explicit approval**;
   - CI results are reported from GitHub;
   - squash merge into `main`;
   - this file is then updated with the outcome.

### 4.4 Acceptance criteria
1. Flyway migrates an empty database; running it again changes nothing; the application starts with `ddl-auto: validate`.
2. The application connects as `wallet_app`, which is not a superuser; Flyway runs as `wallet_owner`.
3. `wallet_app` cannot update, delete or truncate `ledger_entries`, `financial_transactions`, `audit_logs` or `risk_reviews`, or disable their triggers.
4. Unbalanced and single-entry ledger transactions fail at commit; an amount ≤ 0 fails.
5. A negative balance, a second wallet for the same customer, a changed wallet number, or a currency other than THB is rejected.
6. Self-transfer, an unknown status, and a repeated idempotency key from the same sender are rejected; the same key from two different senders is accepted.
7. Negative daily-limit usage and a risk score outside 0–100 are rejected.
8. `SYS-CASH-CLEARING` and `SYS-SUSPENSE` are seeded.
9. `Money` rejects more than 2 decimals and values larger than 19 digits, and never rounds.
10. The domain models enforce no overdraft, consistent hold/release/capture, only the allowed transfer state changes, and balanced postings that follow the templates.
11. ArchUnit fails if a financial domain class, or `common.money`, uses JPA, Hibernate or Spring; a self-test proves it.

## 4B. PR 4 — KYC and wallet (plan accepted 2026-11-03)

### 4B.1 Summary
A customer completes a profile and KYC; a compliance officer approves it, which creates the wallet and its ledger account in the same transaction. The customer can then see the wallet, deposit and withdraw simulated money with limits and idempotency, freeze the wallet, and look up a recipient by wallet number. **This is the first code that changes balances.** Delivered as **PR 4a** (profile, KYC, review, wallet creation, wallet reads, freeze) and **PR 4b** (idempotency, deposits, withdrawals, lookup). No transfers, risk or history (PR 5), no frontend (PR 6), no documents or face verification.

### 4B.2 Decisions (owner, 2026-11-03)
All are recorded in doc 06 (MVP-ADR-10, -12, -19 and -23 amendments) and in doc 02 where the contract changes.

| # | Decision | Owner's condition |

| Q2 | `customer_id` is the auth user id | |
| Q3 | Lookup reads the legal name through an interface in `wallet.application`, implemented by `user.application` | prove that Spring wiring works and the module direction holds (ArchUnit plus a context test) |
| Q4 | JdbcClient, not JPA; `version` checked in SQL | |
| Q5 | `firstName` and `lastName`, at most 100 each, not editable after approval | a legal-name change process may come later |
| Q6 | Document type `ID_CARD` or `PASSPORT`, reference at most 50, always masked | this is a basic KYC review workflow, not identity verification |
| Q7 | `PUT /kyc/applications/{id}` edits a `DRAFT` | owner only; another customer's id gives the identical `404` |
| Q8 | New code `INVALID_KYC_STATE` (409) | |
| Q9 | Customer self-freeze; `ADMIN` freeze and unfreeze with a reason, on the wallet | wallet and ledger account change in **one transaction**, wallet locked first, so the ledger can't take entries for a frozen wallet |
| Q10 | Staff endpoints: KYC list, detail, approve, reject | |

| Q14 | After the idempotency record is purged, return the stored movement only if customer, operation, wallet, amount and currency all match; otherwise `409 IDEMPOTENCY_KEY_REUSED` | **confirmed** (2026-11-04): proven by `MoneyFlowIT` (after a purge and after expiry, the same movement returns the stored response and a different one gives `409`). The deposit note is not compared (Z3, accepted) |
| Q15 | Email shown as `a***@example.com`; phone with only the last 4 digits | |

**Owner's implementation requirements:**
1. Every money operation uses the same lock order.
2. A first request that fails and rolls back must not leave an incomplete idempotency record that blocks a retry; this is tested.
3. `BigDecimal` only; scale validated before processing; never rounded; minimum, maximum and daily limits tested.
4. Daily limits use `BusinessDay` and the injected `Clock`, never the server's time zone.
5. Masking is not encryption; field encryption stays a documented gap.
6. A frozen wallet can't deposit or withdraw, and only authorised staff can unfreeze it. (`CLOSED` is unreachable and final in the MVP, D21 and B3, so nobody reopens it.)
7. Rate limits protect against abuse and wallet-number guessing.

### 4B.3 Affected components
- `user` (all layers): profile, KYC, approval orchestration.
- `wallet` (all layers): creation, reads, freeze, limits, deposits, withdrawals, idempotency, lookup.
- `ledger` (application, persistence): customer account, posting, status.
- `admin` (web): staff endpoints.
- Reused: `audit`, `notification`, `common.security` (`403` audit cap, money rate limit), `common.error`; `auth.application` for contact details.
- New migration `V8__user_create_customers_and_kyc.sql`. Merged V1–V7 don't change.

### 4B.4 Acceptance criteria
1. No wallet before approval: `404` on `GET /wallet`, `403 KYC_REQUIRED` on money endpoints.
2. KYC states and errors; one active application; re-apply after rejection; reason required.
3. Approval creates exactly one wallet and ledger account in one transaction, also when approved concurrently; a failure leaves nothing behind.
4. Only `COMPLIANCE_OFFICER` decides; customers get `403`; another customer's application gives the identical `404`.
5. Deposit and withdrawal update balance, ledger, business row and audit together; a forced failure leaves all unchanged.
6. Limit boundaries at the minimum, maximum and daily limit and ±0.01; usage resets at 17:00 UTC.
7. N concurrent withdrawals never overdraw or exceed a limit; money is conserved; the ledger stays balanced.
8. Same key and body replays the original response, rejections included; a different body gives `409`; another customer's key is separate; concurrent duplicates post once.
