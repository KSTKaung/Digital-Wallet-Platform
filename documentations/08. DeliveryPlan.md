## 2. Planning and delivery procedure
Every PR follows the same steps (CLAUDE.md, `.claude/WORKFLOW.md`):
1. **Plan:**
   - the `plan-feature` skill produces requirements with doc references, affected components, risks, acceptance criteria, test cases, an implementation sequence and open questions;
   - nothing is changed while planning.
2. **Decide:**
   - the owner answers the open questions;
   - decisions that change an MVP rule go into doc 06 (and doc 07 for data), never only into a plan.
3. **Accept:** the owner accepts the plan, and **it is recorded in this file** (§4 onwards).
4. **Implement** in small steps, using the agent and skill named for each step:
   - `backend-engineer`, `frontend-engineer` and `test-engineer`;
   - the skills `database-migration`, `implement-rest-api`, `secure-wallet-transfer` and `testing-workflow`.
5. **Review:**
   - `code-reviewer`, plus `security-reviewer` and/or `database-reviewer` where the workflow gates require them;
   - the main session checks each finding against the code and reports it as confirmed or dismissed.
6. **Verify:**
   - `./mvnw verify`, the frontend checks and a Compose check, as relevant;
   - only results of commands that actually ran are reported.
7. **Deliver:**
   - commit, push, PR and merge, **each only with the owner's explicit approval**;
   - CI results are reported from GitHub;
   - squash merge into `main`;
   - this file is then updated with the outcome.

## 3. PR 1 — Foundation (delivered)

### 3.1 Scope
- **Backend:** one modular Spring Boot 4.1.2 application on Java 21, built with the Maven Wrapper.
  - Empty module packages.
  - `common.error`: `ErrorCode` and `ApiException`.
  - `common.web`: the error body, `GlobalExceptionHandler`, the correlation-ID filter, and the filter that returns 404 for `/internal/**`.
  - `common.security`: deny by default, CORS, JSON 401/403 responses.
- **Architecture tests:** 9 ArchUnit rules with self-tests.
- **Integration tests:** Testcontainers PostgreSQL.
- **Frontend:** React and TypeScript with Vite and Tailwind 4.3.3; the API is reached same-origin through the Vite proxy and nginx.
- **Containers:** multi-stage Dockerfiles running as non-root users; `compose.yaml` with every port bound to 127.0.0.1, and optional Mailpit; `scripts/dev-up.sh` and `scripts/dev-down.sh`.
- **CI:** backend, frontend, Compose, security (Gitleaks, OWASP Dependency-Check 12.2.2 with the `NVD_API_KEY` secret and cached NVD data, npm audit), and the PR-title check. Dependabot, and every action pinned to a commit SHA.
- **Docs:** doc 06 (decision register); the CLAUDE.md, CONTRIBUTING.md and `.claude/` rewrite.

### 3.2 Decisions taken during PR 1
- **Swagger UI dropped:** springdoc `-webmvc-api` only (MVP-ADR-15). The bundled Swagger UI ships DOMPurify with CVSS 10.0 CVEs.
- **Dependency-Check 12.2.2, not 13.0.0** (MVP-ADR-15). A free NVD API key is required in practice; without one the first download took over 4 hours and failed with HTTP 429.
- **CI NVD steps:** update, save to the cache, then scan offline, with a 360-minute job limit.

### 3.3 Verification

### 4.4 Acceptance criteria
1. Flyway migrates an empty database; running it again changes nothing; the application starts with `ddl-auto: validate`.
2. The application connects as `wallet_app`, which is not a superuser; Flyway runs as `wallet_owner`.
3. `wallet_app` cannot update, delete or truncate `ledger_entries`, `financial_transactions`, `audit_logs` or `risk_reviews`, or disable their triggers.
4. Unbalanced and single-entry ledger transactions fail at commit; an amount ≤ 0 fails.
5. A negative balance, a second wallet for the same customer, a changed wallet number, or a currency other than THB is rejected.
6. Self-transfer, an unknown status, and a repeated idempotency key from the same sender are rejected; the same key from two different senders is accepted.
7. Negative daily-limit usage and a risk score outside 0–100 are rejected.
8. `SYS-CASH-CLEARING` and `SYS-SUSPENSE` are seeded.
9. `Money` rejects more than 2 decimals and values larger than 19 digits, and never rounds.
10. The domain models enforce no overdraft, consistent hold/release/capture, only the allowed transfer state changes, and balanced postings that follow the templates.
11. ArchUnit fails if a financial domain class, or `common.money`, uses JPA, Hibernate or Spring; a self-test proves it.

## 4A. PR 3 — Authentication and authorization (delivered)

### 4A.1 Summary
Customers register, verify by email OTP, log in, refresh, log out, and change or reset their password. Every other endpoint requires a valid JWT, and roles are enforced. The PR also adds rate limiting, audit and email sending, and fixes the error-response gaps deferred from PR 1 (MVP-ADR-19). No frontend, profile, KYC or staff-management endpoints.

### 4A.2 Decisions (owner, 2026-11-02)
All are recorded in doc 06 (MVP-ADR-14, -19 and the -23 amendment), and in doc 02 where the contract changes.

| # | Decision |
| --- | --- |
| Q1 | MVP-ADR-14 approved: refresh token in a cookie; refresh and logout also require `X-Requested-With` and an allowed `Origin` |
| Q2 | `register` always returns the same `201`; the owner of a taken email or phone gets a notice email |
| Q3 | every `verify-otp` failure returns `400 INVALID_OTP`; the audit row keeps the real reason |
| Q4 | `resend-otp` always returns `202`; only the per-IP limiter can return `429` |
| Q5 | reset by OTP, then a 15-minute single-use `resetToken`; a reset revokes sessions and clears the lock; `purpose: LOGIN` refused |
| Q6 | `sessions` table and `sid` claim, checked on each request; `last_seen_at` written at most once a minute |
| Q7 | user status `PENDING_VERIFICATION`, `ACTIVE`, `FROZEN`, `SUSPENDED` |
| Q8 | staff accounts from a startup runner and optional environment variables; none seeded by migrations |
| Q9 | `JWT_PRIVATE_KEY`, `JWT_KID`, `OTP_HMAC_SECRET`, `REFRESH_TOKEN_PEPPER` required in every profile, with fail-fast; `scripts/generate-dev-secrets.sh` prints values for the owner to paste into `.env` |
| Q10 | `spring-boot-starter-mail` approved; Mailpit starts by default in Compose; a send failure does not fail the request |
| Q11 | phone format: E.164 pattern only |

Dependencies: `spring-boot-starter-oauth2-resource-server` (MVP-ADR-05), `bcprov-jdk18on` (MVP-ADR-23), `spring-boot-starter-mail` (Q10). The rate limiter is an in-house filter.

### 4A.3 Affected components
- `auth` (all layers); `audit.application`; `notification.application`.
- `common.security`: JWT resource server, method security, rate-limit filter, CSRF filter for the cookie endpoints, and a `SessionValidator` interface that `auth.application` implements.
- `common.web` and `common.error`: deferred handlers, `ErrorController`, new codes.
- Config: `pom.xml`, `application*.yaml`, `compose.yaml`, `.env.example`, nginx `X-Forwarded-For`, `server.forward-headers-strategy`.
- New migration `V7__auth_create_auth.sql`: `users`, `credentials`, `password_history`, `login_failure_counters`, `sessions`, `refresh_tokens`, `otp_challenges`, `password_reset_tokens`.

### 4A.4 Acceptance criteria
1. Register, verify and log in works end to end; before verification, login gives the identical `401`.
2. Duplicate registration is indistinguishable from a new one.
3. Password lengths 11 and 129 are rejected, 12 and 128 accepted; each of the last 5 is rejected.
4. Lock at the 5th consecutive failure, expiry at 15 minutes, reset on success, password reset clears it, owner emailed; identical `401` throughout.
5. All OTP limits hold; responses as in Q3 and Q4; a code is single-use.
6. Refresh rotates; reusing a rotated token revokes the family; the cookie has the required attributes and is absent from the body.
7. Refresh or logout without the header or from a foreign `Origin` gives `403`.
8. A request is refused after logout, password change, 30 idle minutes or freeze.
9. `401` for missing, expired or tampered tokens; `403` by role; `429` with `Retry-After`.
10. MVP-ADR-19's deferred gaps are fixed.
11. Only hashes in the database; no OTP, password or token in logs or audit rows.
12. Startup fails when a required secret is missing.
