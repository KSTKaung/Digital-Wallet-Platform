## PR 2: Database and financial domain
**Status:** merged 2026-10-30 as PR #16 (`e07696b`). Delivery record: #17. PR #15 carried the requirements and decisions beforehand.

### Decisions
Planning decisions Q1–Q9 are in doc 08 §4.2. The main ones:
- Full tables for the financial core and audit; `auth`, `usr` and `notification` got schemas only.
- JPA entities deferred to the PRs that use them.
- Wallet number: 11 digits with a Luhn check digit. Transfer description: at most 140 characters, never logged.
- Flyway history in its own schema. Trigger functions kept per schema.

Decisions made during implementation:
- **Decimals are value-based:** `1.0000` is accepted, `1.001` rejected.
- **`sender_risk_state` can't be deleted.**
- **The JaCoCo coverage gate was turned on now,** not later. It was proven to fail at a 99% threshold.

## PR 3: Authentication and authorization
**Status:** merged 2026-11-02 as PR #18 (`fb6490b`).

### Decisions (plan accepted 2026-11-02)
| # | Decision |
| --- | --- |
| Q1 | MVP-ADR-14 approved: refresh token in a `Secure; HttpOnly; SameSite=Strict` cookie; refresh and logout also require `X-Requested-With` and an allowed `Origin` |
| Q2 | `register` always returns the same `201`; the owner of a taken email or phone gets a notice |
| Q3 | Every `verify-otp` failure returns `400 INVALID_OTP`; the audit row keeps the real reason |
| Q4 | `resend-otp` always returns `202` |
| Q5 | Reset by OTP, then a 15-minute single-use token |
| Q6 | `sessions` table and `sid` claim, checked per request |
| Q7 | User status `PENDING_VERIFICATION`, `ACTIVE`, `FROZEN`, `SUSPENDED` |
| Q8 | Staff accounts from a startup runner and optional environment variables |
| Q9 | Four required secrets, with fail-fast at startup |
| Q10 | `spring-boot-starter-mail` approved; Mailpit starts by default |
| Q11 | Phone format: E.164 pattern only |

**Decided during the work:**
- At most 4 concurrent password hashes.
- Remaining malformed requests return `400`.
- Sessions end at most 7 days after login, access tokens included.
- A foreign `Origin` gets the documented error body.
- A wrong current password doesn't count towards lockout.
- Fixed Compose subnet, so the backend trusts only nginx.
- `generate-dev-secrets.sh` added to the backend CI path filter.

### Bugs found by testing, not review

### First review round (`security-reviewer`, `database-reviewer`, `code-reviewer`)
No Critical findings. Verdict: not ready to merge.

**The one High: account pre-hijack (H1 in the security report).** An attacker registers `victim@x` with their own password. The real owner registers later, gets the same `201`, and their password is dropped. When the owner verifies the emailed code, the row holding the **attacker's** password and phone becomes active.
**Fix:** re-registering an unverified account replaces its password and phone and cancels the old code, and `verify-otp` for registration also requires the password. A code alone no longer activates anything.

| --- | --- | --- | --- |
| F1 | Refresh and revocation took locks in opposite orders, so a revocation could roll back with a `500` | High (database), Low (security) | Session before token everywhere |
| F2 | Cancelling a code before its 5th guess avoided the 24-hour block: about 480 guesses a day instead of 25 | Medium | Cap total wrong guesses at 25 |
| F3 | A reset token or code survived a password change for up to 15 minutes | Medium | Invalidated in the same transaction |

| F6 | The successful `OTP_VERIFY` audit ran after commit | Medium | Inside the transaction |
| F7 | A NUL byte in an identifier gave `500` | Low/Minor | Refused with `400` |

**Dismissed:** the CI path filter finding (already fixed); an index for the hourly session purge (it would slow the per-minute session write).

**Owner decisions G1–G7:**
- G1: accept the takeover fix.
- G2: unverified accounts expire after 24 hours.
- G3: at most one owner notice per hour.
- G4: IPv6 rate-limit key by /64.
- G5: burning a victim's OTP limits is an accepted trade-off.
- G6: a registrant can learn whether a phone is taken; accepted trade-off.
- G7: logout with an expired access token returns `401`; accepted.

### Open risks (doc 06 MVP-ADR-23)
| Risk | Stays open until |
| --- | --- |
| **Phone squatting:** an attacker re-registers a victim's phone every 24 hours, blocking it indefinitely | Phone verification exists |
| **Limiter table full:** at 100,000 keys, new clients get `429` on `/auth/**` for up to a minute | The limiter's capacity is increased |
| **Audit volume:** an authenticated user can cause up to 300 `403` audit rows a minute | Re-assessed in the PR adding role-restricted endpoints (PR 4) |

### Other accepted limits
- Re-registering an unverified email cancels the owner's code, so a repeating attacker can delay verification but can't take the account.
- The rate limiter is in memory, correct only for one instance, and a burst across a window boundary can reach twice the limit.
- No breached-password check, MFA or step-up.

## What these reviews taught us
- **Real runs find what tests miss.** The secrets-script bug passed the whole suite and failed in the first real start.
- **Fixes need review too.** Three fixes in PR 2 and PR 3 introduced or exposed a further issue (C2 led to E1; E5 dropped a rule; the G2 purge led to the race in H1).
- **Review rounds stop when findings get small,** by owner decision, rather than running until nothing is left.
