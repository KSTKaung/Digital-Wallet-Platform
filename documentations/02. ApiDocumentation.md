## 1. Conventions

### 1.1 Surfaces
| Prefix | Audience | On Gateway |
| ------ | -------- | ---------- |
| `/api/v1/**` | customers, merchants, staff, SPA | Yes |
| `/api/v1/webhooks/**` | external providers | Yes — public, signature-verified, no JWT |
| `/internal/v1/**` | services and ops only (mutual TLS) | **No** |

### 1.2 Authentication
`Authorization: Bearer <accessToken>` everywhere except endpoints marked *public*: register, login, refresh, verify-otp, resend-otp, forgot-password, reset-password and the webhooks. Access tokens last 15 minutes; refresh tokens last 7 days and rotate on use. The JWT `roles` claim is an array drawn from `CUSTOMER`, `MERCHANT`, `ADMIN`; staff permissions are resolved from `admin_db` roles.

### 1.3 Headers
| Header | Direction | Notes |
| ------ | --------- | ----- |
| `Authorization` | request | JWT |
| `Idempotency-Key` | request | **Required** on deposits, withdrawals, transfers, payments, QR confirm, refunds, bill payments. Client-generated UUID v4: version 4 and the RFC variant are both checked; any other value gives `400 VALIDATION_ERROR` naming the header, never the value. |
| `X-Correlation-Id` | request (optional) / response | generated by the Gateway when absent; echoed in errors and events |
| `Retry-After` | response | on 429 and 503 |

### 1.4 Idempotency
First request executes. Replay with the same key and body returns the original status and body. Same key with a different body → `409 IDEMPOTENCY_KEY_REUSED`. Keys are retained 24 h in Redis and in `idempotency_records` (database unique constraints remain the final guard).

**MVP (owner, 2026-11-04):**
- PostgreSQL only, no Redis.
- **Expiry is checked on every request,** not left to the purge job: a key whose 24 h have passed is treated as new and replaced under its row lock, so a concurrent request with the same key waits and sees the replacement.
- **After expiry, a completed request stays bound to its movement (owner, 2026-11-04, Y5):** the deposit or withdrawal row keeps the key, unique per customer. A request with that key returns the original movement if customer, operation, wallet, amount and currency all match (doc 08 Q14), and `409 IDEMPOTENCY_KEY_REUSED` otherwise. Only a stored refusal, or a record with no outcome, lets an expired key run a new request.
- **Stored and replayed rejections:** `INSUFFICIENT_BALANCE`, `SINGLE_LIMIT_EXCEEDED`, `DAILY_LIMIT_EXCEEDED` and `WALLET_FROZEN`. One key gets one answer; to try again after an unfreeze or a top-up, the client sends a new key.
- **Not stored (the key is not consumed):** `KYC_REQUIRED` is a precondition checked before the key is used, and validation errors and server errors leave no record, so a retry with the same key runs fresh.
- **Replay:** the original status, error code and body, with the current request's `correlationId` and `timestamp`.
- **Key scope:** a key is unique per customer and operation, `(customer_id, operation, key)`. Another customer's identical key is a separate key: it never replays the first customer's response and never returns 409.
- **Request hash:** SHA-256 of the validated request in canonical form (fixed amount scale, currency), so formatting differences don't cause a false 409.
- **Rejected requests:** a business-rule rejection (for example `INSUFFICIENT_BALANCE` or a limit error) is stored and replayed with its original status. The rejection is stored in its own transaction, because the money transaction rolls back.

These three rules were decided by the owner on 2026-10-30 (doc 07 §7).

### 1.5 Pagination
`?page=0&size=20` (size 1–100). List endpoints return `{ "items": [...], "page": { page, size, totalElements, totalPages } }`. OpenAPI v1.0.0 returns bare arrays for some lists; the wrapped form is the target for all lists from v1.1.

### 1.6 Data types
UUID ids; ISO-8601 UTC timestamps; ISO-4217 currency (`THB` only in MVP); money as JSON numbers with **at most 2 decimals**, handled as decimals server-side (D-15). A non-zero digit after the second decimal is rejected with `400 INVALID_AMOUNT`, never rounded; trailing zeros such as `1.0000` are accepted as `1.00` (doc 06 MVP-ADR-21).

### 1.7 Error model
```json
{ "success": false, "errorCode": "INSUFFICIENT_BALANCE",
  "message": "Available balance is lower than the requested amount",
  "correlationId": "uuid", "timestamp": "2026-08-24T10:00:00Z" }
```
| HTTP | Meaning |
| ---- | ------- |
| 400 | validation error |
| 401 | missing, invalid or expired token; bad credentials (generic message) |
| 403 | role, permission, ownership or KYC requirement denied |
| 404 | not found; also returned for other customers' resources |
| 409 | conflict: duplicate, insufficient balance, limit exceeded, idempotency reuse, cancel after completion |
| 422 | unbalanced ledger posting (internal) |
| 415 | unsupported media type |
| 429 | rate limited |
| 502/504 | provider failure or timeout (card gateway, biller, verification) |
| 503 | `SERVICE_DEGRADED` (D-13) |

**Error codes:** `INSUFFICIENT_BALANCE`, `DAILY_LIMIT_EXCEEDED`, `SINGLE_LIMIT_EXCEEDED`, `WALLET_FROZEN`, `WALLET_NOT_FOUND`, `SELF_TRANSFER`, `BENEFICIARY_BLOCKED`, `RISK_BLOCKED`, `INVALID_AMOUNT`, `CURRENCY_MISMATCH`, `KYC_REQUIRED`, `KYC_ALREADY_ACTIVE`, `INVALID_KYC_STATE` (409, doc 06 MVP-ADR-19), `INVALID_OTP`, `OTP_EXPIRED`, `OTP_ATTEMPTS_EXCEEDED`, `ACCOUNT_LOCKED`, `IDEMPOTENCY_KEY_REUSED`, `INVALID_TRANSFER_STATE` (409, doc 06 MVP-ADR-19), `RATE_LIMITED` (429) and `UNSUPPORTED_MEDIA_TYPE` (415) (doc 06 MVP-ADR-19), `SERVICE_DEGRADED`, `QR_EXPIRED`, `MERCHANT_NOT_APPROVED`, `REFUND_EXCEEDS_PAYMENT`, `CARD_NOT_FOUND`, `CARD_DECLINED`, `CARD_EXPIRED`, `BILLER_UNAVAILABLE`, `BILL_INQUIRY_FAILED`, `BILL_PAYMENT_PENDING`, `FACE_MISMATCH`, `LIVENESS_FAILED`, `VERIFICATION_ATTEMPTS_EXCEEDED`, `CONSENT_REQUIRED`, `SYSTEM_ERROR`. The shared `ErrorCode` enum lives in the common module (Sprint 0).

### 1.8 Rate limits (Gateway, Redis)
| Scope | Limit |
| ----- | ----- |
| `/api/v1/auth/**` | 10 requests/min per IP; account lock after 5 failed logins |
| Money POSTs (deposits, withdrawals, transfers, payments, bill payments, card link) | 30/min per customer |
| Face verification | 3 attempts per KYC application |
| OTP resend | 60 s cooldown, at most 5 per hour per identifier; counts stored in PostgreSQL; a limit silently sends nothing and still returns `202` (doc 06 MVP-ADR-23) |
| Wallet lookup | 10/min per authenticated user and 30/min per client IP, sliding windows stored in PostgreSQL. Successful and failed lookups both count. `429` with `Retry-After`; every counted lookup audited, while refusals for format, caller status or the limit are neither counted nor audited (doc 06 MVP-ADR-20, X1–X3) |
| Webhooks | 600/min per provider |
| Everything else | 300/min per user |

URI versioning (`/api/v1`). Additive changes stay in v1; breaking changes require `/api/v2`. Events carry `eventVersion`.

### 2.1 Identity (`Auth`)
| Method | Path | Auth | Request | Success | Errors |
| ------ | ---- | ---- | ------- | ------- | ------ |
| POST | `/api/v1/auth/register` | public | `{email, phoneNumber, password}` | 201 `{email, status: PENDING_VERIFICATION}`, identical for a new and an existing account (doc 06 MVP-ADR-23) | 400 |
| POST | `/api/v1/auth/login` | public | `{email, password}` | 200 `{accessToken, expiresIn: 900}`; refresh token in a cookie (doc 06 MVP-ADR-14) | 401 (identical for a wrong password, an unknown account and a locked account; doc 06 MVP-ADR-23) |
| POST | `/api/v1/auth/refresh` | refresh cookie, `X-Requested-With`, allowed `Origin` | — | 200 `{accessToken, expiresIn: 900}`; rotated cookie | 401, 403 |
| POST | `/api/v1/auth/logout` | bearer, `X-Requested-With`, allowed `Origin` | — | 204; clears the cookie | 401, 403 |
| POST | `/api/v1/auth/verify-otp` | public | `{otp, purpose: REGISTRATION\|PASSWORD_RESET, identifier, password}`; `password` is required for `REGISTRATION` | 200, empty for `REGISTRATION`; `{resetToken}` for `PASSWORD_RESET` | 400 `INVALID_OTP`, identical for every failure (doc 06 MVP-ADR-23) |
| POST | `/api/v1/auth/resend-otp` | public | `{identifier, purpose}` | 202 always, also for unknown identifiers or when a limit sends nothing; `PASSWORD_RESET` behaves like `forgot-password` | 400 (malformed body), 429 only from the per-IP limit |
| POST | `/api/v1/auth/forgot-password` | public | `{email}` | 202 always | |
| POST | `/api/v1/auth/reset-password` | public | `{resetToken, newPassword}` | 200 | 400 |
| POST | `/api/v1/auth/change-password` | bearer | `{currentPassword, newPassword}` | 200; ends every session and clears the cookie | 400 (policy or reuse), 401 |

Rules: OTP is single-use, valid 5 minutes, 5 attempts; five failed logins lock the account temporarily; sessions expire after 30 minutes of inactivity; refresh tokens are revocable; every login is audited.

**MVP values (doc 06 MVP-ADR-23):**
- Lockout: 5 consecutive failures lock the account for 15 minutes.
- Login response: wrong password, unknown account and locked account all return the **same `401`**. `403 ACCOUNT_LOCKED` is not returned by login.
- Passwords: 12–128 characters, none of the last 5 passwords, hashed with Argon2id.
- OTP:
  - 6 digits;
  - resend after a 60-second cooldown, at most 5 per hour;
  - a resend cancels the previous code;
  - after 5 used-up challenges in 24 hours the identifier gets no new challenge until the window clears.
- A successful password reset clears a lockout, and the owner is emailed when an account is locked.
- Reset token: valid 15 minutes, single-use.
- `register` on an email still `PENDING_VERIFICATION` replaces its password and phone and cancels the live code; for any other status, or a phone owned by another account, it only notifies the owner. The response never differs.
- `verify-otp`: a missing or wrong `password` for `REGISTRATION` gives the identical `400 INVALID_OTP` and costs an attempt. `password` is ignored for `PASSWORD_RESET`.
- Email and identifier fields refuse control characters and lengths over 254; password fields refuse lone surrogates (`400 VALIDATION_ERROR`).
- A JWT with a wrong or missing `kid` gets the generic `401`.

| GET | `/api/v1/wallets/lookup?walletNumber=` | | exact wallet-number match → `{maskedName, maskedWalletNumber}`; identical `404` for a missing, frozen, closed or own wallet; rate-limited and audited (doc 06 MVP-ADR-20) |

Money values are JSON numbers with exactly two decimals (`1234.50`, `0.00`).

`DepositResponse` / `WithdrawalResponse`: `{id, walletNumber, amount, status, reference, ledgerStatus}` (doc 06 MVP-ADR-10 amendment: the internal wallet id is not exposed).

**MVP deposits and withdrawals (PR 4b; doc 06 MVP-ADR-03, -13, -18, -21, -22; doc 07 D10):**
- **Request:** deposit `{amount, currency, reference?}`, withdrawal `{amount, currency}`. `reference` is an optional free-text note of at most 100 characters (no control or format characters, at least one letter or digit). It is stored with the deposit and is part of the request hash, but it is not returned and never appears in logs or audit rows. `fundingSource` is not part of the MVP (no cards or banks, MVP-ADR-12): any value is refused with `400 VALIDATION_ERROR` (`fundingSource: is not supported`), and an explicit `null` counts as absent (owner, 2026-11-04, W3). Other unknown fields are ignored.
- **Response:** `201` with `status` `COMPLETED` (the only MVP status), the server-generated unique `reference` (`DEP-…` or `WDR-…`, also the ledger `transaction_reference`) and `ledgerStatus` `POSTED`. The response is returned only after the commit.
- **Errors, in the order they are checked:**
  1. `400 VALIDATION_ERROR`: missing or invalid `Idempotency-Key`, missing `amount` or `currency`, or an invalid `reference`;
  2. `400 INVALID_AMOUNT`: more integer digits than `NUMERIC(19,2)` holds (`amount: is too large`, owner, 2026-11-04, Y3), more than 2 decimals (never rounded), or zero or negative. The amount is judged before the currency (Y2);
  3. `400 CURRENCY_MISMATCH`: any currency other than `THB`;
  4. `403 KYC_REQUIRED`: no wallet yet (KYC not approved);
  5. `409 IDEMPOTENCY_KEY_REUSED`, or the replay of a stored outcome (§1.4);
  6. `409 WALLET_FROZEN`;
  7. `400 INVALID_AMOUNT` below the minimum, `409 SINGLE_LIMIT_EXCEEDED`, then `409 DAILY_LIMIT_EXCEEDED` (Asia/Bangkok day; deposits and withdrawals each have a daily limit, MVP-ADR-18);
  8. `409 INSUFFICIENT_BALANCE` (withdrawals).

  Steps 1–4, and the minimum in step 7, do not consume the key; the stored rejections are listed in §1.4. A stored rejection gets one `FAILURE` audit row, a replay none (doc 06 MVP-ADR-03 amendment, W5).
- **Rate limit:** 30 money POSTs per minute per customer (§1.8), in addition to the general per-user limit.
- No email is sent for a deposit or withdrawal in the MVP; transaction emails come with transfers (PR 5).

**MVP wallet lookup (PR 4b; doc 06 MVP-ADR-19, -20):** `GET /api/v1/wallets/lookup?walletNumber=` (query string only, never a path segment).
- **Validation, in two independent steps (owner, 2026-11-04, X2):**
  1. **Format:** `walletNumber` must be exactly 11 ASCII digits, otherwise `400 VALIDATION_ERROR` (missing: `walletNumber: parameter is required`). Checked first, before the caller checks; not counted, not audited.
  2. **Check digit:** after the rate-limit check and after the attempt is recorded, a wrong Luhn check digit gives the identical generic `404`, with no wallet query, and is counted and audited (`FAILURE`, `NOT_FOUND`) exactly like a missing wallet.
- **Caller:** no wallet yet gives `403 KYC_REQUIRED`; a frozen wallet gives `409 WALLET_FROZEN`. Nothing is counted.
- **Limits:** 10 per minute per user and 30 per minute per client IP (IPv6 per /64), sliding windows in PostgreSQL measured by the database clock at the time each statement starts, after the lookup's advisory locks are held, so a wait for the lock does not shift the window (owner, 2026-11-04, Y1). A shared address (NAT) shares the per-IP count and its `Retry-After`; accepted (Z4). Found and not-found lookups both count. Over a limit: `429 RATE_LIMITED` with `Retry-After` (the whole seconds until the oldest counted attempt leaves the window, at least 1); a refused request is neither counted nor audited.
- **Response:** `200 {maskedName, maskedWalletNumber}`: the first name plus the last name's initial (`Somchai J.`), and the number with only its last 4 digits visible (`*******8901`). Exact match only. A missing, frozen or closed wallet, or the caller's own, gives the identical generic `404 NOT_FOUND`.
- **Audit:** one row per counted lookup (action `WALLET_LOOKUP`, `SUCCESS` with the found wallet's internal id, or `FAILURE`), in the transaction that records the attempt. It holds neither the wallet number nor a name.
- Attempts older than the window are purged by a scheduled job.

### 2.4 Transfer (`Transfer`, `Beneficiary`)
| Method | Path | Notes |
| ------ | ---- | ----- |
| POST | `/api/v1/transfers` | `{receiverCustomerId, beneficiaryId?, amount, currency, description}`; Idempotency-Key; 201 `Transfer`; 409/403/503 |
| GET | `/api/v1/transfers` | paged |
| GET | `/api/v1/transfers/{id}` | participants only |
| GET | `/api/v1/transfers/{id}/status` | `{status, ledgerStatus}` |
| POST | `/api/v1/transfers/{id}/cancel` | pending only; 409 if completed |
| GET, POST | `/api/v1/beneficiaries` | list / `{beneficiaryCustomerId, nickname}` |
| GET, PUT, DELETE | `/api/v1/beneficiaries/{id}` | delete sets `DELETED` |

Transfer status: `PENDING → PROCESSING → COMPLETED | FAILED | CANCELLED`. `COMPLETED` means both wallets were updated; `ledgerStatus` shows accounting posting.

**MVP (doc 06 MVP-ADR-03, MVP-ADR-20, MVP-ADR-24):**
- **Request:** `receiverWalletNumber` replaces `receiverCustomerId`, and `beneficiaryId` is not used.
- **Statuses:** `COMPLETED`, `PENDING_REVIEW`, `REJECTED`, `CANCELLED`, `EXPIRED` and `BLOCKED`.
- **Responses:**
  - `201` with `COMPLETED` (risk `ALLOW` or `MONITOR`);
  - `201` with `PENDING_REVIEW` (risk `MANUAL_REVIEW`: the amount is held for at most 24 hours, and the recipient receives nothing yet);
  - `500 SYSTEM_ERROR` if the risk evaluation fails (nothing moves; never treated as score 0);
  - `403 RISK_BLOCKED` (risk `BLOCK`; the transfer is recorded as `BLOCKED`).
- **Ineligible recipient:** a missing, frozen or closed wallet returns the same `404` as the lookup. The sender's own wallet returns `SELF_TRANSFER`.
- **Cancel:** allowed only while the transfer is `PENDING_REVIEW`; otherwise `409 INVALID_TRANSFER_STATE`.
- **Limits:** minimum 1.00 THB; at most 50,000.00 THB per transfer; daily 100,000.00 (`BASIC`) or 500,000.00 THB (`FULL`) (MVP-ADR-18).

### 3.1 KYC documents and face verification (Customer & KYC)
| Method | Path | Role | Notes |

| POST | `/api/v1/kyc/applications/{id}/documents` | CUSTOMER | `{documentType: ID_CARD\|PASSPORT\|SELFIE\|PROOF_OF_ADDRESS, contentType, sizeBytes}` → 201 `{documentId, uploadUrl, expiresAt}`; client uploads the file to the pre-signed URL (encrypted storage) |

## 7. Client-side and SDK guide (React demo)

1. Call only the Gateway (`VITE_API_BASE_URL=http://localhost:8080`); never service ports or `/internal/v1/**`.
2. Keep the access token in memory; do not persist refresh tokens in `localStorage`; on 401 refresh once, then sign out.
3. Create a UUID `Idempotency-Key` when the confirm screen opens; reuse it for retries and double-clicks; discard after a terminal response.
4. Treat `404 WALLET_NOT_FOUND` as "complete KYC first" and route to the KYC screen.
5. Show `ledgerStatus`: `PENDING_POST` as a subtle "Accounting pending" chip next to *Completed*; `FAILED_POST` as a support-contact notice.
6. Never decide limits, KYC outcome or permissions in the browser.
7. Cards: load the gateway's hosted-fields script, send only the returned token to `POST /api/v1/cards`; never read or log card numbers.
8. Face verification: capture selfie via the provider's SDK, show consent text, upload with the pre-signed URL.
9. Handle 503 `SERVICE_DEGRADED` by showing the retry-after time; handle 429 with backoff.
10. Generate a typed client from OpenAPI (`openapi-typescript` plus a thin `fetch` wrapper). Suggested layout:
```
web-app/src/api/{client.ts,auth.ts,kyc.ts,wallet.ts,transfers.ts,payments.ts,cards.ts,bills.ts,admin.ts}
web-app/src/auth/{tokenStore.ts,AuthProvider.tsx}
```
Quick start:
```
curl -X POST http://localhost:8080/api/v1/auth/login -H 'Content-Type: application/json' -d '{"email":"a@example.com","password":"…"}'
curl http://localhost:8080/api/v1/wallet/balance -H "Authorization: Bearer $TOKEN"
```
