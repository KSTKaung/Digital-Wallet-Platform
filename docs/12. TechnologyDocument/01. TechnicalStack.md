# Digital Wallet Platform — Technical Planning
## Technical Stack

Aligned with [FInal/01. ArchitectureDocument.md](../11.%20ArchitectureDesign/FInal/01.%20ArchitectureDocument.md) §9. Architecture is **microservices**, not a modular monolith (ADR-002).

### Core Backend
**Language/Framework:**
- Java 21 (BRD technical constraint)
- Spring Boot 3.x

**Key Spring modules:**
- Spring Web (REST)
- Spring Data JPA / Hibernate
- Spring Security + JWT
- Spring Validation
- Spring Boot Actuator

**Build tool:**
- Maven (one module per deployable service)

**Architecture style:**
- **8 business microservices + 3 infrastructure components**
- Domain-Driven Design (bounded contexts)
- Clean Architecture **inside each service** (`presentation → application → domain ← infrastructure`)
- REST for request/response; Kafka for cross-service **side effects** only

### Business services and databases
| Service | Database |
| ------- | -------- |
| Identity | `identity_db` |
| Customer & KYC | `customer_db` |
| Wallet | `wallet_db` |
| Transfer | `transfer_db` |
| Payment & Merchant | `payment_db` |
| Ledger | `ledger_db` |
| Risk & Notification | `risk_db` / `notification_db` |
| Admin & Operations | `admin_db` |

### Infrastructure components
- **API Gateway** — Spring Cloud Gateway (JWT, routing, rate limit, CORS, correlation IDs)
- **Config Server** — Spring Cloud Config
- **Service Discovery** — Eureka, or platform-native on Kubernetes

### Database Layer
**Primary DB:** PostgreSQL, **database-per-service** (no cross-service SQL joins).

**Wallet schema (operational):**
- Snapshot `available_balance` and `reserved_balance`
- Optimistic locking via `wallets.version` (ADR-009)
- CHECK constraints: balances ≥ 0

**Ledger schema (accounting system of record):**
- Double-entry: every financial transaction posts balanced debit + credit
- Entries are immutable; corrections are reversals + new transactions

**Migrations:**
- Flyway **per service** (own `db/migration` against that service’s database)

**Connection pooling:**
- HikariCP

### Caching
- Redis: rate-limit counters, OTP, idempotency keys, optional balance **read** cache (invalidate on wallet write)
- Concurrency on wallet updates: **optimistic `version`**, not distributed locks as the primary mechanism

### Security & Auth
- Identity Service issues JWT access + refresh pairs
- Gateway validates JWT on inbound public routes (ADR-008)
- RBAC in Admin & Operations; `@PreAuthorize` in each service
- BCrypt/Argon2 password hashes; TLS in transit
- Internal APIs (`/internal/v1/**`) stay off the public gateway

### Transaction Integrity & Async Processing
- `Idempotency-Key` on all money-movement POSTs
- Wallet/Transfer call Ledger over **internal REST** on the request path
- Transactional **outbox** then Kafka (`TransferCompleted`, `MoneyDeposited`, …) for notification, audit, risk consumers
- No 2PC across services (ADR-007)

### API Layer
- OpenAPI source of truth: `docs/11. ArchitectureDesign/FInal/03. ApiSpecification.yaml`
- Springdoc per service; Gateway is the public entry (`localhost:8080` locally)

### Frontend (demonstration only)
- **React + TypeScript + Vite** SPA in `web-app/` — not a microservice and not in the Final 8+3 map
- Consumes Gateway `/api/v1/**` only; see `17. FrontendUi.md`
- Backend remains the system of record; UI has no ledger or KYC decision logic

### Testing
- JUnit 5 + Mockito
- Testcontainers (Postgres / Redis / Kafka as needed per service)
- k6 or Gatling for transfer throughput

### DevOps & Infrastructure
- Docker + Docker Compose for local (see `15. LocalDevelopment.md`)
- Kubernetes + GitHub Actions for CI/CD
- AWS as deployment target (RDS, ElastiCache, Kafka, ECS/EKS)

### Observability
- SLF4J + Logback structured JSON
- Micrometer + Prometheus + Grafana
- Correlation IDs on Gateway and events (`correlationId` in the event envelope)
- Tracing: Micrometer Tracing / OpenTelemetry across REST and consumers
