# Banking Digital Wallet — Business Rules
## 1. Authentication
### Registration
- Email/mobile number must be unique.
- Password must satisfy minimum security requirements.
- Password must be securely hashed.
- New accounts start with **_PENDING_VERIFICATION_**.
- Account becomes active only after successful OTP verification.
- OTP must expire after a defined period.
- OTP retry attempts must be limited.

### Login
- Invalid credentials must not reveal whether the account exists.
- Account is temporarily locked after repeated failed login attempts.
- Inactive/frozen users cannot perform normal login operations.
- Access tokens must expire after a defined period.
- Refresh tokens must be revocable.
- Every successful login must create a security/audit event.

## 2. Customer
- Customer email must be unique.
- Customer phone number must be unique.
- Customer can access only their own profile.
- Required KYC information must be completed before restricted financial operations.
- Frozen customers cannot initiate financial transactions.
- Suspended customers cannot access restricted services.
- Sensitive customer information must be masked where appropriate.
- Important profile changes must be audited.

## 3. KYC & Compliance
- Customer must submit all required KYC information.
- Required identity documents must be provided.
- KYC application starts with **_PENDING_**.
- Only authorized compliance staff can approve/reject KYC.
- Rejected KYC applications must include a rejection reason.
- A customer can have only one active KYC application.
- KYC must be approved before high-risk financial operations are enabled.
- KYC status changes must be audited.
- KYC documents must only be accessible to authorized personnel.

## 4. Wallet
### Wallet Creation
- Each customer must have at least one wallet.
- Wallet number must be unique.
- Wallet must belong to exactly one customer.
- Wallet must have a defined currency.
- New wallet balance starts at **_0_**.
- Wallet status starts as **_ACTIVE_** when account requirements are satisfied.

### Wallet Status
- **_ACTIVE_** wallet can perform permitted operations.
- **_FROZEN_** wallet cannot perform financial transactions.
- **_CLOSED_** wallet cannot be reactivated unless explicitly allowed by business policy.
- Wallet status changes must be audited.

## 5. Deposit
- Deposit amount must be positive.
- Wallet must exist.
- Wallet must be active.
- Customer must be authorized to access the wallet.
- Deposit must not exceed the maximum deposit limit.
- Deposit must create a transaction record.
- Deposit must update the financial ledger.
- Deposit operation must be atomic.
- Duplicate deposit requests must not create duplicate transactions.
- Failed deposits must not modify the wallet balance.

**Example:**
```
Deposit 10,000 THB

Before:
Balance = 20,000

After:
Balance = 30,000
```

## 6. Withdrawal
- Withdrawal amount must be positive.
- Wallet must exist.
- Wallet must be active.
- Customer must be authorized.
- No overdraft.
- Available balance must be greater than or equal to withdrawal amount.
- Daily withdrawal limit must be enforced.
- Per-transaction withdrawal limit must be enforced.
- Withdrawal must create a transaction record.
- Withdrawal must update the ledger.
- Withdrawal must be atomic.
- Failed withdrawal must not change the balance.

**Example:**
```
Balance = 20,000 THB
Withdrawal = 25,000 THB

→ REJECTED
→ Balance remains 20,000 THB
```

## 7. Transfer (Important)
- Sender must have enough available balance.
- Sender and recipient must exist.
- Sender must be active.
- Recipient must be active.
- Cannot transfer to self.
- Transfer amount must be positive.
- Transfer must not exceed the per-transaction limit.
- Daily transfer limit = 100,000 THB for the default customer tier.
- Sender and recipient currency must be compatible.
- Frozen wallets cannot transfer money.
- Transfer must be atomic.
- Sender must be debited exactly once.
- Recipient must be credited exactly once.
- Transfer must have a unique transaction reference.
- Transfer must support idempotency.
- Duplicate requests with the same idempotency key must not create duplicate transfers.
- Failed transfers must roll back the financial operation.
- Successful transfers must generate a transaction event.
- Transfer status must be tracked.

**Example:**
```
Transfer: 10,000 THB

Sender
20,000 → 10,000

Recipient
5,000 → 15,000
```

## 8. Transfer Limits
| Customer Tier | Daily Transfer Limit |
| ------------- | -------------------: |
| Basic         |          100,000 THB |
| Verified      |          500,000 THB |
| Premium       |        1,000,000 THB |

**Rules:**
- Daily limit is calculated based on successful transfers.
- Failed transfers do not consume the daily limit.
- Cancelled transfers do not consume the daily limit.
- A transfer exceeding the customer's limit must be rejected.
- Limits must be configurable rather than hard-coded.
- Limit changes require appropriate authorization.
- Limit changes must be audited.

## 9. Beneficiary
- Beneficiary must have valid account information.
- Customer cannot add an invalid account.
- Customer cannot add themselves as a beneficiary.
- Beneficiary must be associated with the customer who created it.
- Duplicate beneficiaries should be prevented.
- Deleted beneficiaries cannot be used for new transfers.
- High-risk beneficiary changes may require additional verification.

## 10. Payment
- Customer must be authenticated.
- Customer wallet must be active.
- Merchant must be active.
- Payment amount must be positive.
- Customer must have sufficient balance.
- Payment must not exceed transaction limits.
- Customer must explicitly confirm the payment.
- Payment must have a unique payment reference.
- Payment must be atomic.
- Duplicate payment requests must not create duplicate payments.
- Successful payment must debit the customer and credit the merchant according to the ledger model.

## 11. QR Payment
- QR code must belong to a registered merchant.
- QR code must be valid.
- Expired QR codes cannot be used.
- Customer must verify merchant information before confirmation.
- Payment amount must be positive.
- Customer must have sufficient balance.
- Customer must explicitly confirm payment.
- QR payment must generate a unique transaction reference.
- Duplicate QR payment requests must be prevented.
- Invalid QR codes must be rejected.

## 12. Merchant
- Merchant must complete registration.
- Merchant must pass required KYC/business verification.
- Merchant must be approved before accepting payments.
- Merchant ID must be unique.
- Suspended merchants cannot receive new payments.
- Merchant transactions must be isolated from other merchants.
- Merchant settlement must follow the configured settlement schedule.
- Merchant profile changes must be audited.

## 13. Refund
- Refund must reference an original payment.
- Original payment must exist.
- Original payment must be completed.
- Refund amount must be positive.
- Refund amount cannot exceed the original payment amount.
- A payment cannot be refunded more than its original amount.
- Refund must create a separate financial transaction.
- Original transaction must never be deleted.
- Refund status must be tracked.
- Refund approval may require an authorized merchant/admin user.
- Refund operations must be auditable.

## 14. Bill Payment
- Customer must have an active wallet.
- Bill provider must be active.
- Bill amount must be positive.
- Customer must have sufficient balance.
- Bill payment must have a unique reference.
- Duplicate bill payment requests must be prevented.
- Failed external provider transactions must not result in an incorrect wallet debit.
- External provider reference must be stored.
- Bill payment status must support at least:

> PENDING  
> SUCCESS  
> FAILED  

## 15. Transaction
- Every financial operation must generate a transaction.
- Transaction ID must be unique.
- Transaction reference must be unique.
- Transaction amount must be positive.
- Transaction currency must be defined.
- Transaction status must be tracked.
- Completed transactions must not be physically deleted.
- Financial transactions must be immutable.
- Corrections must be performed through reversal/adjustment transactions.
- Every transaction must be traceable to its originating business operation.
- Every transaction must have a correlation/reference ID.
- Transaction creation must be idempotent where applicable.

## 16. Ledger / Double-Entry Accounting
- Every completed financial transaction must have corresponding ledger entries.
- Every debit must have a corresponding credit.
- Total debit must equal total credit.
- Ledger entries must be immutable.
- Completed ledger entries cannot be deleted.
- Financial corrections must create new entries.
- Ledger operations must be atomic.
- Ledger balance must be consistent with ledger entries.
- A transaction cannot be marked **_COMPLETED_** if its required ledger entries were not successfully created.

**Example:**
```
Transfer 10,000 THB

Ledger
────────────────────────
Sender       DEBIT   10,000
Recipient    CREDIT  10,000
────────────────────────
Total        =       10,000
```

## 17. Fraud & Risk
- Every high-value transaction must be evaluated against risk rules.
- Transactions exceeding configured risk thresholds may require additional verification.
- Suspicious transactions can be flagged.
- Blocked transactions must not modify financial balances.
- Fraud alerts must be recorded.
- Risk decisions must be auditable.
- Fraud rules must be configurable.
- Risk officers can investigate fraud alerts.
- A blocked transaction cannot be completed without authorized intervention.

**Example:**
```
IF amount > 50,000
AND new_device = true
THEN
    risk = HIGH
    require additional verification
```

## 18. Notification
- Successful transfers must generate transaction notifications.
- Successful payments must generate transaction notifications.
- Failed financial operations should generate appropriate notifications.
- Security events should generate security notifications.
- Notification failure must not roll back a completed financial transaction.
- Failed notifications must be retried.
- Permanently failed messages should be moved to a Dead Letter Queue.
- Notification preferences must be respected where applicable.

## 19. Admin
### Customer Management
- Only authorized admins can view customer management data.
- Only authorized admins can freeze/unfreeze customers.
- Freeze reason must be recorded.
- Customer freeze/unfreeze must be audited.
- Admin cannot access information beyond their permission scope.

### Transaction Management
- Admins can view transactions according to their permissions.
- Admins cannot directly modify completed financial transactions.
- Financial corrections must use controlled adjustment/reversal processes.
- Sensitive operations require appropriate authorization.

### Merchant Management
- Authorized admins can approve/reject merchants.
- Merchant rejection must contain a reason.
- Merchant suspension must be audited.

## 20. Admin Approval / Maker-Checker
- The user who creates a sensitive request cannot approve their own request.
- Approval must come from an authorized role.
- Approval must be recorded.
- Rejection must include a reason.
- Approved operations can be executed only once.
- Approval requests must have an expiration period.
- All approval actions must be audited.

**Example:** 
```
Finance Officer A
       │
       ▼
Create Refund Adjustment
       │
       ▼
PENDING_APPROVAL
       │
       ▼
Finance Officer B
       │
    ┌──┴──┐
    ▼     ▼
 APPROVE REJECT
    │
    ▼
 Execute
```

## 21. RBAC & Authorization
- Every protected API must require authentication.
- Every administrative API must require authorization.
- Users can have one or more roles according to the system design.
- Roles contain permissions.
- Permissions define allowed operations.
- Users cannot access resources outside their authorization scope.
- Admins cannot grant permissions beyond their own authority.
- Auditor role should be read-only.
- Authorization failures must be logged.

## 22. Audit
- Login/logout
- Password changes
- KYC decisions
- Wallet freeze/unfreeze
- Customer status changes
- Transfers
- Payments
- Refunds
- Admin actions
- Permission changes
- Configuration changes
- Fraud decisions
- Financial adjustments

```
Actor
Action
Resource
Resource ID
Timestamp
Result
IP Address
Correlation ID
```

## 23. Settlement
- Only completed eligible transactions can be settled.
- Failed transactions must not be settled.
- Each transaction must be settled only once.
- Settlement amount must equal eligible transaction amounts minus applicable fees.
- Settlement batch must have a unique reference.
- Settlement status must be tracked.
- Settlement results must be auditable.

## 24. Reconciliation
- Internal transactions must be compared against external records.
- Each external transaction must be uniquely identifiable.
- Matched transactions are marked **_RECONCILED_**.
- Unmatched transactions become reconciliation exceptions.
- Reconciliation must be repeatable.
- Reconciliation must not modify original transaction history.
- Reconciliation exceptions require investigation.
- Reconciliation results must be auditable.

## 25. System-Level Rules
### Data Integrity
- Financial data must never be silently deleted.
- Financial operations must be transactional.
- Database constraints must protect critical relationships.
- Monetary values must use **_BigDecimal_**, not floating-point types.
- Currency must always be explicitly represented.

### Idempotency
**For Operation:**
```
Deposit
Transfer
Payment
Refund
Bill Payment
```

**Example: If the same request arrives twice**
```
Request 1 → Transfer created
Request 2 → Return existing result
```
