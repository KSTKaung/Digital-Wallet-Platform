# Product Backlog
Treating the Product Backlog as a real enterprise Agile backlog rather than simply a feature list.
Using:
- Story Points: 1, 2, 3, 5, 8, 13
- Priority: Must / Should / Could / Won't
- Sprint: 2-week sprint
- Acceptance Criteria: concise, testable conditions
- MVP: Sprints 1–10 **in this backlog’s story table**
- Hardening / advanced capabilities: Sprints 11–14

**Delivery sequencing** for the 8-service architecture is [13. SprintPlanning.md](13.%20SprintPlanning.md) (Gateway/Identity → KYC → Wallet+Ledger → Transfer → Payment → Admin). If a story’s “Sprint” column here disagrees with that plan, keep the story and AC; **implement in the Sprint Planning slice**. Architecture and APIs: Final folder under `11. ArchitectureDesign`.

## Epic 1 — Authentication & Security
| ID      | Story                       | SP | Priority | Sprint |
| ------- | --------------------------- | -: | -------- | ------ |
| AUTH-01 | Register                    |  5 | Must     | 1      |

| AUTH-08 | Multi-Factor Authentication |  3 | Should   | 2      |

### AUTH-01 — Register
**Acceptance Criteria**
- User can register with a unique email/mobile number.
- Duplicate email/mobile is rejected.
- Password meets security requirements.
- Password is securely hashed.
- Account is created in PENDING_VERIFICATION state.
- OTP verification is initiated.

### AUTH-02 — Verify OTP
**Acceptance Criteria**
- User can submit the OTP.
- Valid OTP activates the account.
- Expired OTP is rejected.
- Invalid OTP is rejected.
- OTP has a maximum retry count.
- OTP cannot be reused.

### AUTH-03 — Login
**Acceptance Criteria**
- Valid credentials authenticate successfully.
- Invalid credentials return an appropriate error.
- JWT access token is generated.
- Refresh token is generated.
- Locked/inactive accounts cannot log in.
- Failed attempts are recorded.

### AUTH-04 — Refresh Token
**Acceptance Criteria**
- Valid refresh token generates a new access token.
- Expired refresh token is rejected.
- Revoked refresh token is rejected.
- Token rotation is supported.

### AUTH-05 — Logout
**Acceptance Criteria**
- User can invalidate the active refresh token.
- Subsequent refresh attempts fail.
- Audit event is generated.

### AUTH-06 — Change Password
**Acceptance Criteria**
- Current password must be verified.
- New password must meet security requirements.
- Old password cannot be reused.
- Existing sessions can be invalidated after password change.

### AUTH-07 — Reset Password
**Acceptance Criteria**
- User can request password reset.
- Reset token/OTP expires.
- Token can only be used once.
- New password is securely stored.

### AUTH-08 — Multi-Factor Authentication
**Acceptance Criteria**
Customer can enable MFA.
OTP/TOTP verification is required.
Login requires second factor when enabled.
Customer can disable MFA after authentication.
