# Service Decomposition

> Working paper. **Approved spec:** [`FInal/01. ArchitectureDocument.md`](FInal/01.%20ArchitectureDocument.md) and [`FInal/03. ApiSpecification.yaml`](FInal/03.%20ApiSpecification.yaml).

## Target architecture
> API Gateway + Microservices + DDD + Clean Architecture + Event-Driven Communication

## Transfer Service
**Responsibility**
Handles customer-to-customer money transfers.

**Features**
- Transfer
- Beneficiary
- Transfer Limits
- Transfer Status
- Idempotency
- Transfer Validation

**APIs**
```
POST /api/v1/transfers

GET  /api/v1/transfers
GET  /api/v1/transfers/{id}

GET  /api/v1/transfers/{id}/status

POST /api/v1/transfers/{id}/cancel
```
**Beneficiary APIs:**
```
GET    /api/v1/beneficiaries
POST   /api/v1/beneficiaries
GET    /api/v1/beneficiaries/{id}
PUT    /api/v1/beneficiaries/{id}
DELETE /api/v1/beneficiaries/{id}
```

**Own Database**
```
transfer_db
├── transfers
├── beneficiaries
├── transfer_limits
└── idempotency_records
```

**Important Rules**
- Sender must have sufficient balance
- Sender cannot transfer to self
- Amount must be positive
- Daily limit must be enforced
- Transfer must be atomic
- Duplicate requests must not create duplicate transfers

**Publishes Events**
- TransferInitiated
- TransferCompleted
- TransferFailed
- TransferCancelled

## Ledger Service (a special and highly protected financial service)
**Features**
- Double-Entry Accounting
- Debit
- Credit
- Ledger Entries
- Financial Transactions
- Balance Calculation
- Reversal

**APIs**
```
POST /internal/v1/ledger/entries

GET  /internal/v1/ledger/accounts/{accountId}

GET  /internal/v1/ledger/transactions/{transactionId}

GET  /internal/v1/ledger/accounts/{accountId}/entries

POST /internal/v1/ledger/transactions/{transactionId}/reverse
```

**Own Database**
```
ledger_db
├── ledger_accounts
├── ledger_entries
├── financial_transactions
└── reversals
```

**Important Rules**
- Debit must equal Credit
- Ledger entries are immutable
- Completed transactions cannot be deleted
- Financial correction requires a reversal/adjustment
- Financial operation must be atomic

**Example**
```
Transfer 10,000 THB

Ledger
────────────────────────────
Sender Account       DEBIT    10,000
Recipient Account    CREDIT   10,000
────────────────────────────
                    Balanced
```

## API Gateway
The API Gateway is the single entry point for external clients.
```
Customer App
      │
      ▼
 API Gateway
      │
 ├────┼────┬────┬────┬────┐
 ▼    ▼    ▼    ▼    ▼    ▼
Auth Wallet Transfer Payment Customer Admin
```

**Features**
- Routing
- Authentication
- JWT validation
- Rate limiting
- Request logging
- CORS
- API versioning
- Correlation ID
- Load balancing
- Security headers

**Example:**
```
/api/v1/auth/**       → Identity Service
/api/v1/customers/**  → Customer Service
/api/v1/wallet/**     → Wallet Service
/api/v1/transfers/**  → Transfer Service
/api/v1/payments/**   → Payment Service
/api/v1/admin/**      → Admin Service
```

## Redis
Redis for supporting concerns rather than financial source-of-truth data.
- JWT/session-related caching
- Rate limiting
- Idempotency keys
- Temporary OTP data
- Distributed locks where appropriate
- Frequently accessed configuration

## Service Communication
Two Communication Patterns
**Synchronous — REST**
Use for immediate request/response operations.
```
API Gateway
     │
     ▼
Transfer Service
     │
     ▼
Wallet Service
```

**Asynchronous — Kafka**
Use for events and side effects.
```
Transfer Service
      │
      ▼
TransferCompleted
      │
      ▼
     Kafka
   ┌──┼───────┐
   ▼  ▼       ▼
Audit Risk Notification
```
