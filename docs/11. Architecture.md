## Why Domain-Driven Design(DDD)?
DDD is particularly suitable because this project system has many complex business domains.
These are modules from previous system analysis which is not a simple CRUD modules.
> Identity
> Customer
> KYC
> Wallet
> Ledger
> Transfer
> Payment
> Merchant
> Refund
> Fraud
> Settlement
> Reconciliation
> Admin
> Notification
> Audit

They are different in
- Business rules
- Entities
- Responsibilities
- Transactions
- Security requirements
- Data ownership
- Workflows
DDD gives Bounded Contexts.

**Example:**
```
┌────────────────────┐
│ Wallet Context     │
│                    │
│ Wallet             │
│ Balance            │
│ WalletLimit        │
└────────────────────┘

┌────────────────────┐
│ Transfer Context   │
│                    │
│ Transfer           │
│ Beneficiary        │
│ TransferLimit      │
└────────────────────┘

┌────────────────────┐
│ Ledger Context     │
│                    │
│ Account            │
│ LedgerEntry        │
│ Transaction        │
└────────────────────┘
```
This prevents everything from becoming one giant domain model.
DDD allows each context to maintain its own model.

## Why Clean Architecture?
DDD tells the business boundaries.
Clean Architecture tells how to structure the implementation.
```
┌─────────────────────────────────────┐
│          API / Presentation         │
│                                     │
│ Controllers / REST / DTOs           │
└──────────────────┬──────────────────┘
                   │
┌──────────────────▼──────────────────┐
│          Application Layer          │
│                                     │
│ Use Cases / Application Services    │
└──────────────────┬──────────────────┘
                   │
┌──────────────────▼──────────────────┐
│             Domain Layer            │
│                                     │
│ Entities / Value Objects / Rules    │
│ Domain Services / Domain Events     │
└──────────────────┬──────────────────┘
                   │
┌──────────────────▼──────────────────┐
│         Infrastructure Layer        │
│                                     │
│ PostgreSQL / Kafka / Redis / AWS    │
└─────────────────────────────────────┘
```

### Dependency Rule
Dependencies should point toward the domain.
```
Controller
    ↓
Application
    ↓
Domain
    ↑
Infrastructure
```
The domain should not depend on:
- Spring
- PostgreSQL
- Kafka
- Redis
- AWS
This makes the business logic easier to test.

**Example:**
For the **Transfer Service**, instead of putting everything into:
```
TransferController
```
Should separate responsibilities.

**For Presentation:**
> TransferController

**Responsible for:**
> POST /api/v1/transfers

**For Application:**
> CreateTransferUseCase

**Responsible for orchestrating:**
> 1. Validate request
> 2. Find sender
> 3. Find recipient
> 4. Check balance
> 5. Check limits
> 6. Fraud evaluation
> 7. Execute transfer
> 8. Publish event

## Why Microservices?
Microservices are appropriate because domains of this project have relatively clear boundaries.

**Example:**
- Customer Service
- Wallet Service
- Transfer Service
- Payment Service
- Merchant Service
- Ledger Service
- KYC Service
- Fraud Service
- Notification Service
- Settlement Service
- Admin Service

Each service owns its own business responsibility.

**Example:**
Use relative DB per domain.
```
Customer Service
      │
Customer DB

Wallet Service
      │
Wallet DB

Transfer Service
      │
Transfer DB

Ledger Service
      │
Ledger DB
```

It is useful because can independently scale:
```
Payment Service
       ↑
High traffic
       │
Scale independently
```
While
```
Admin Service
       │
Lower traffic
       │
Fewer instances
```

## Why Event-Driven Architecture?
A banking wallet generates many events.

**Example:**
```
TransferCompleted
PaymentCompleted
DepositCompleted
WithdrawalCompleted
KycApproved
FraudAlertCreated
WalletFrozen
RefundCompleted
```
These events can be published to Kafka.

```
                 Transfer Service
                        │
                        │
                        ▼
              TransferCompleted
                        │
                        ▼
                      Kafka
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
   Notification      Fraud         Audit
      Service        Service       Service
```

Event-Driven Is Valuable because it suppose a transfer succeeds
**Without events:**
```
Transfer
   │
   ├── call Notification
   ├── call Audit
   ├── call Fraud
   ├── call Reporting
   └── call Analytics
```
This creates tight coupling.

**With events:**
```
Transfer
   │
   ▼
TransferCompleted
   │
   ▼
Kafka
 ┌─┼─────────┬─────────┐
 ▼ ▼         ▼         ▼
Notification Audit    Reporting
```
Now the Transfer Service doesn't need to know who consumes the event.

## Synchronous vs Asynchronous Communication
Use REST when an immediate response is required without making everything event-driven.
**Example:**
```
Customer
   │
   ▼
POST /transfers
   │
   ▼
Transfer Service
   │
   ▼
Validate
   │
   ▼
Response
```

Use Kafka events for asynchronous side effects.
```
TransferCompleted
        │
        ▼
      Kafka
     /  |   \
    /   |    \
   ▼    ▼     ▼
Email Audit Notification
```

**Synchronous**
```
Request → Validate → Execute → Response
```
**Asynchronous**
```
Business Event → Kafka → Consumers
```

## Architecture Decision Matrix
| Architecture           | Suitable?       | Why                                                                  |
| ---------------------- | --------------- | -------------------------------------------------------------------- |
| **Microservices**      | ✅ Yes           | Clear domain boundaries, independent deployment/scaling              |
| **Clean Architecture** | ✅ Yes           | Keeps financial business logic independent of infrastructure         |
| **DDD**                | ✅ **Essential** | Complex banking domains require bounded contexts and domain modeling |
| **Event-Driven**       | ✅ **Yes**       | Useful for transactions, notifications, fraud, audit and integration |
